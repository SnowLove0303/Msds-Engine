## 1. 结论

用户对这个弹窗“廉价、很 AI、和全局 UI 不统一”的感受有明确的视觉和代码依据。

最突出的问题是：**白色文档工作台上弹出了一个独立的深蓝控制面板；面板内部又叠加了亮蓝边框、蓝底卡片、彩色 emoji、重复徽标、等宽小字和强调提示框。每个元素都试图被注意，却没有清楚地区分选择信息、文件信息和最终操作。**

“很 AI”在本报告中是对模板化视觉语言的描述，不是对代码由谁生成的事实判断。导致这种观感的是一组可识别的组合：深色科技风底板、成排高亮卡片、包装箱/幼苗/楼房/灯泡/火箭图标，以及“同步覆写多版本批量导出”“立即同步打包导出”等技术词叠加。它们与当前以白色、灰色边框、深青色按钮为主的文档工具气质不匹配。

建议保留居中弹窗和现有版本选择能力，采用**浅色对话框、紧凑选择列表、简洁业务文案、单一主按钮**。第一轮优化集中在弹窗本身，不需要重做编辑器或引入新的前端组件框架。

还有一个必须更新的事实：**本目录当前代码在多个文件时已经只下载一个 ZIP。** 不能继续把旧工作区“逐个 DOCX 加 ZIP 重复下载”的问题当作这个版本的现状。

## 3. 当前全局风格是什么

从截图背景与当前 CSS 看，页面主体已有明确的简洁工具型风格：

| 项目 | 当前全局实现 | 弹窗当前做法 | 造成的差异 |
|---|---|---|---|
| 主表面 | 白色页面与白色面板 | 深蓝 #0b192c | 像切换到了另一个产品 |
| 主文字 | 深灰 #202a33 | 浅白 #e2e8f0 / #f1f5f9 | 与全局主题脱节 |
| 强调色 | 深青 #2b7188 | 天蓝、亮青混用 | 选择项与主按钮使用不同强调语言 |
| 边框 | 中性灰色细边框 | 青色外框和蓝色选中框 | 几乎每一层都在强调 |
| 按钮 | 约 5px 圆角、无重阴影 | 主按钮复用全局，但处于深色页脚 | 白色取消按钮尤其突兀 |
| 弹窗参照 | 批注弹窗已有白色表面 | 导出单独写深色样式 | 相似组件没有共享视觉规范 |

需要统一的是弹窗表面、文字、列表和状态，不应把全局界面改成深色来迁就一个弹窗。现有白色批注弹窗可作为内部视觉参照，但不能直接继承它全部结构或假定它的可访问性已验证。

## 4. 截图中的问题与影响

### UI-01：局部深色主题与全局浅色界面断裂

**证据：** 白色文档编辑器被遮罩压暗，中央弹窗则使用深蓝底、青色外边框和重黑阴影。正文、标题、页脚各自又有细小的深浅变化。

**影响：** 用户需要重新适应另一套视觉语言。深色本身不是问题，问题在于它没有沿用产品其他页面的表面、文字与边框规范。

**建议：** 改为白色表面、深灰正文、中性边框；主按钮继续沿用全局深青色。背景遮罩只负责分离层级，避免过重模糊和阴影共同制造“舞台式弹窗”。

### UI-02：全部选中时，整列蓝卡片使强调失去作用

**证据：** 截图中基础版本和四个预设版本均被选中，形成五块类似的蓝色卡片。每项同时有复选框、彩色图标、标题、文件名和右侧标签。

**影响：** 蓝色从“选择反馈”变成整片背景。每项的信息层级不清楚，用户难以快速核对版本和文件名。

**建议：** 改成同一列表内的行结构。复选框为主要选择信号，选中行仅使用很浅的品牌色底或轻边框。不要同时叠加重底色、亮边框、图标和徽标。

### UI-03：彩色 emoji 没有承担必要的信息任务

**证据：** 标题有包装箱，基础文档有幼苗，预设有楼房/齿轮，说明有灯泡，确认按钮有火箭。

**影响：** 图标来自不同语义和绘制风格，增加花哨感；“火箭”和“幼苗”对确认 MSDS 导出内容没有实质帮助。不同系统的 emoji 呈现还可能不同。

**建议：** 标题、说明和确认按钮直接使用文字。若需要文件图标，只用一个统一的单色样式；复选框已经能表达选择，无需额外装饰。

### UI-04：标题和按钮文案堆叠技术词

**证据：** 标题“同步覆写多版本批量导出”，主按钮“立即同步打包导出”，正文解释“自动注入……字段覆写差量”。

**影响：** 用户正在决定导出哪些版本，却先读到实现机制。标题过长，“立即”“同步”等词没有帮助判断交付物。

**建议：** 标题用“批量导出”；说明用“选择需要导出的版本，未修改的内容沿用基础文档。”；按钮根据实际输出显示“导出 ZIP（5 份）”或“导出 DOCX（1 份）”。

### UI-05：重复标签占空间，缺少真正有用的摘要

**证据：** 除基础行外，每个预设右侧都显示“衍生版本”；行内又重复“底模”和“处专属覆写字段”。

**影响：** “衍生版本”对每行都一样，无法帮助比较。相较之下，界面没有直接突出“共导出几份、是否包含基础版、ZIP 叫什么”。

**建议：** 按“基础文档 / 预设版本”分组，去掉每行重复的衍生徽标。将目标模板与修改数量放在次级信息中，底部提供数量与文件名摘要。

### UI-06：文件名太像代码，长名称可读性不足

**证据：** 文件名为亮蓝色、11px、等宽字体；主标题同时拼接预设名称和目标模板。中文长名称与英文文件名挤在一个窄弹窗里。

**影响：** 用户核对实际交付物时需要读文件名，但它被压成一行细小的技术文本。预设名、目标模板和文件名之间也缺少稳定对齐。

**建议：** 预设名称为主行，文件名为独立次行；用常规字体和可读的次级文字色。目标模板用简短辅助字段。长文件名可换行，必要时提供完整名称查看，不只依赖 hover。

### UI-07：ZIP 说明被做成醒目提示卡，抢占了列表注意力

**证据：** 底部用蓝色描边和灯泡图标强调“统一打包……不产生多余弹窗与重复下载”。

**影响：** 正常交付规则被呈现为特殊提示。“不产生多余弹窗与重复下载”属于历史修复说明，用户更关心本次将得到什么。

**建议：** 改为普通摘要：“将导出 5 份 DOCX，打包为 1 个 ZIP。” 下方显示压缩包名称；不再使用强调提示卡。

### UI-08：基础文档的强制包含没有解释

**证据：** 基础文档复选框 checked 且 disabled，无法取消。

**影响：** 禁用复选框容易被误解为无权限或组件失效，用户不知道这是业务规则。

**建议：** 第一轮保留当前包含基础文档的行为，并明确显示“基础文档，始终包含”，使用只读包含状态。是否允许只导出预设版本属于后续产品选项，不应在改色时顺手改变。

## 5. 源码解析：风格为什么无法统一

### 5.1 弹窗表面直接写死在 HTML 中

renderPresetExportModal 在 main.js 第 530-531 行附近：

```html
<div class="modal-backdrop" data-backdrop="true"
     style="position:fixed;inset:0;background:rgba(0,0,0,.65);
            backdrop-filter:blur(4px);display:flex;align-items:center;
            justify-content:center;z-index:9999;">
  <div class="modal-card preset-export-dialog"
       style="background:#0b192c;border:1px solid rgba(91,214,210,.3);
              border-radius:12px;width:540px;max-width:92vw;
              box-shadow:0 20px 40px rgba(0,0,0,.6);overflow:hidden;">
```

**解析：** 全局已经用 --panel、--ink、--line 等变量描述浅色界面，弹窗却直接写入深色背景和浅色文字。只改全局变量无法改变这些固定值；普通 CSS 的背景声明也不能自然覆盖 inline style。

**改法：** 将结构与颜色分开。用 .export-dialog 和 .dialog-backdrop 等 class 表达组件，表面、文字、边框与阴影统一由变量控制。移除局部主题色，而不是继续追加 !important 对抗内联样式。

### 5.2 同一选中状态被重复定义

styles.css 第 1581 行附近：

```css
.preset-export-item.active {
  border-color: #0ea5e9;
  background: rgba(14, 165, 233, 0.08);
}
```

第 1916 行附近又覆盖：

```css
.preset-export-item.active {
  background: rgba(14, 165, 233, 0.14) !important;
  border-color: rgba(56, 189, 248, 0.5) !important;
}
```

**解析：** 同一个状态有两份定义，后者用 !important 锁定颜色。若只调整前者，实际页面仍可能显示旧蓝色。

**改法：** 合并为唯一的选中状态规则，引用品牌色的浅色状态 token。检查未选中、hover、focus-visible、disabled 与 selected 五种状态是否相互区分。

### 5.3 文件名使用独立的亮蓝色规则

styles.css 第 1598 行附近：

```css
.preset-item-filename {
  color: #38bdf8;
  font-size: 11px;
  font-family: var(--font-mono, monospace);
}
```

**解析：** 文件名承担内容核对任务，却被做成类似终端路径的视觉样式；其颜色也不跟随全局次级文字变量。

**改法：** 改用全局文本字体、次级文字色和 12-13px 的候选字号。允许长名称断行；设置列表内容容器 min-width: 0，防止长文件名撑坏布局。候选字号需在真实缩放下验证。

### 5.4 按钮部分复用全局样式，容器却仍是深色

页脚背景硬编码 #081322，取消按钮使用全局 button-quiet；全局白色主题的 .button 又把基础按钮设为白底深灰字。

**解析：** 同一弹窗混用了“局部深色容器”和“全局浅色组件”。截图中的白色取消按钮并不是一个孤立问题，而是主题混用的结果。

**改法：** 统一整个弹窗的表面和文字主题，再复用全局主/次按钮。不要只给取消按钮换色，留下深色卡片和亮蓝文字。

### 5.5 字段计数不等于成功应用计数

main.js 当前显示：

```js
Object.keys(p.fieldOverrides || {}).length
```

**解析：** 这表示已存储的键数量，并没有验证非空值、当前模板能否定位或导出是否成功应用。直接写成“处专属覆写字段”可能被用户理解为已确认有效。

**改法：** 在第一轮视觉改造中可简化为“配置了 6 项覆盖”，或把它降为可选详情；若未来要显示“有效修改 6 项”，必须采用实际有效覆盖统计，不能只换文案假装已经验证。

## 6. 与选择和确认有关的交互问题

### 6.1 勾选动作会立即改变长期默认值

第 2853 行附近，复选框 change 会写入 p.enabledForExport 并调用 PresetStore.savePresets。用户之后点击“取消”只是关闭弹窗，不会恢复这次勾选前的默认值。

**当前事实：** “本次选择”与“下次默认选择”耦合。

**建议：** 弹窗打开时创建本次选择草稿，取消则丢弃草稿；确认导出使用本次草稿。如果产品需要记住选择，使用明确的“记住本次选择”选项，或至少说明会记住，不要让普通取消暗含保存默认值。

### 6.2 缺少可见的生成中状态和重复点击保护

executeBatchPresetExport 会显示“正在生成”的 toast，但当前弹窗按钮没有对应的 busy/disabled 状态；点击 handler 直接再次调用该异步函数。

**代码风险：** 用户等待时重复点击可能再次启动生成。本文没有实际触发重复下载。

**建议：** 确认后立即锁定本次选择快照；按钮显示“正在生成…”，禁用重复确认。真实进度可得时显示“已完成 2/5”，不可得时只展示阶段，不伪造百分比。

### 6.3 打开弹窗时的预览对象可能与实际导出对象不同

弹窗预览文件名从 state.editor.engine 读取；执行导出时，预设编辑模式使用 state.editor.normalEngine 作为基础文档。

**风险：** 在两者的型号或页眉页脚信息不同时，预览文件名与真实导出文件名可能不一致，需运行核对。

**建议：** 弹窗和导出共用同一个“本次导出计划”，统一生成基础引擎、版本清单、文件名与数量，避免各处重复推算。此处只涉及导出前确认的信息一致性，不要求重写 DOCX 引擎。

### 6.4 键盘、滚动和错误反馈需要完整验证

当前弹窗 markup 没有声明 role="dialog"、aria-modal 或标题关联；打开 handler 主要设置布尔状态并 renderApp，未见该弹窗专用的初始焦点、焦点限制和返回焦点逻辑。当前容器还缺少明确的视口最大高度和正文滚动约束。

这些是代码层面的缺口和检查点，不能仅凭截图宣布具体浏览器已经出现焦点逃逸或溢出。

**建议：** 设置对话框语义；打开后聚焦标题/首个可选项，Tab 在弹窗内移动，关闭后回到触发按钮。列表较长时只滚动正文，标题和操作区保持可见。导出失败在弹窗内给出清楚原因并保留选择，不依赖瞬时 toast。

## 7. 推荐方案：浅色紧凑导出确认框

### 7.2 版本信息的顺序

每行只保留最能影响选择的内容：

1. 复选框与预设名称；
2. 实际输出文件名；
3. 必要时显示目标语言/主体或覆盖配置摘要。
