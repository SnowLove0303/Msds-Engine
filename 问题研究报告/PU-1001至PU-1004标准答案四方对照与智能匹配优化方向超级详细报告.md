## 1. 结论先行

当前智能匹配存在一个容易被统计数字掩盖的核心问题：

四个产品的智能匹配模型都报告了 16 个 Section、77 个匹配字段、0 个未匹配字段，但最终写入模板后的结构和内容仍没有稳定接近标准答案。

当前最大问题集中在四个阶段之间没有闭环：

1. 源文件事实已经识别出来，但没有形成完整、可追溯的事实台账；
2. 语义匹配模型能够生成 matchedRows，但 matchedRows 到模板行和值格的投影不稳定；
3. 缺失字段、模板示例值和源级说明行没有按照标准答案的章节策略处理；
4. 写入时没有完整保留源段落边界、独立开行和模板槽位关系。

主要差异如下：

| 优先级 | 章节 | 已确认差异 | 影响 |
|---|---|---|---|
| P0 | Section 2 | 分类、标签要素、警示词、象形图、H/P 说明被压缩进少数大值块 | 标签和值结构失去独立语义 |
| P0 | Section 11 | 当前保留大量模板端点和无数据资料行，标准答案只保留源级可用性说明 | 模板示例和空值行残留 |
| P0 | Section 12 | 当前保留 12.1、12.2、12.3 等模板行，标准答案只保留源级生态说明 | 源无端点却继续显示模板项目 |
| P0 | Section 15 | 法规顺序错位，GB 15258 在写入容量不足时丢失 | 源事实缺失，标准结构破坏 |
| P0 | Section 4/5 | PU-1002、PU-1003、PU-1004 仍保留模板示例类急救和消防值 | 源事实被模板内容遮盖 |
| P1 | Section 3 | PU-1002 的源成分名被缩短为通用名称 | 源文案保真失败 |
| P1 | Section 5 | 当前把独立句子合并成一段，标准答案保留语义换行 | 阅读结构和源段落边界丢失 |
| P1 | Section 1 | 个别型号前空格和推荐用途措辞与标准答案不一致 | 产品身份和格式规范不稳定 |
| P2 | 入口 | 页面看起来接受 .doc，但识别引擎实际只接受 .docx | 用户无法按真实原始文件直接完成识别 |

Section 3、Section 8、Section 9、Section 10、Section 13、Section 14、Section 16 的当前结构相对稳定，可以作为保留现有逻辑、补充审计的基线。

## 3. 入口层发现：界面接受 .doc，但识别引擎拒绝 .doc

当前文件选择器包含 .doc，页面也提示支持 .doc；但 docx-engine.js 的 loadDocx 在入口处要求文件名必须以 .docx 结尾。

真实链路是：

文件选择器接受 .doc
    -> loadDocx 检查扩展名
    -> 非 .docx 直接抛出 UNSUPPORTED_EXTENSION
    -> 用户无法得到识别结果

因此本次必须先用 Word 只读打开原始 .doc，再保存为临时 .docx，才能进入当前识别/匹配引擎。

这会产生三个用户风险：

1. 用户以为文件已进入识别，实际上只进入原件提示或预览状态；
2. .doc 转 .docx 可能改变文本框、嵌套表格、域、分页和部分格式；
3. 出现差异时无法快速判断是格式转换问题还是智能匹配问题。

### 入口优化建议

方案 A：网页只声明支持 .docx。

- 文件选择器删除 .doc；
- 页面明确提示“识别模块只支持 .docx”；
- .doc 进入明确错误状态；
- 这是最容易验收的方案。

方案 B：真正支持 .doc。

- 本地受控转换器把 .doc 转成临时 .docx；
- 记录原始文件 SHA-256、转换工具、转换时间和转换结果 SHA-256；
- 转换失败进入 unreadable，而不是 source_absent；
- 转换后重新检查表格、合并、图片、嵌套表格和页眉页脚；
- 原始 .doc 仍然是事实证据，临时 .docx 只是解析副本。

如果目标是用户可以直接导入这些历史原始文件，必须采用方案 B；在没有转换审计前，不应继续在 UI 上宣称 .doc 已经支持。

## 4. 当前匹配统计与真实质量的差距

四个产品当前模型统计相同：

| 指标 | PU-1001 | PU-1002 | PU-1003 | PU-1004 |
|---|---:|---:|---:|---:|
| totalSections | 16 | 16 | 16 | 16 |
| matchedSectionsCount | 16 | 16 | 16 | 16 |
| matchedFields | 77 | 77 | 77 | 77 |
| prunedFields | 14 | 14 | 14 | 14 |
| unmatchedFields | 0 | 0 | 0 | 0 |
| reviewAmbiguousFields | 0 | 0 | 0 | 0 |
| notApplicableFields | 6 | 6 | 6 | 6 |
| injectedCount | 81 | 81 | 81 | 81 |
| prunedCount | 22 | 22 | 22 | 22 |

这些数字不能证明结果接近标准答案：

- matchedRows 只说明语义模型认为找到了事实；
- injectedCount 只说明调用过写入入口；
- prunedFields 不代表最终 DOCX 已经删除整行；
- unmatchedFields 为 0 不能发现模板示例残留；
- 没有比较标准答案时，统计系统无法发现章节拆分、法规顺序、源句换行和独立端点差异。

必须新增第二层质量指标：

source fact
    -> semantic key
    -> template row binding
    -> target value cell
    -> exported DOCX reload
    -> exact value and structure audit

任何值在导出重载后没有出现在预期值格，都必须判定为 projection_error，而不能继续算作 matched。

## 6. Section 1：产品身份、中文名称和推荐用途

旧 MSDS Skill 的 Section 1 规则要求：

- 1.1 产品名称可为空；
- 中文名称值等于源中文产品名 + 一个 ASCII 空格 + 型号；
- 公司信息只能由公司覆盖层控制；
- 推荐用途保留源文案或使用已审核的规范化规则。

PU-1002 的标准答案使用：

水性聚氨酯光亮剂树脂 PU-1002

当前结果使用：

水性聚氨酯光亮剂树脂PU-1002

型号前半角空格缺失。PU-1002 的推荐用途也存在当前结果与标准答案之间的文字差异。这个差异必须进一步区分：

- 型号前空格是可自动验收的格式规范；
- 推荐用途差异必须由 source fact 和 approved normalization 解释；
- 不能由匹配引擎自行把源句改写成模板想要的句子。

优化方式：

1. product_name、model、recommended_use 使用三个独立语义槽；
2. 中文名称由受控 writer 统一拼接一个半角空格；
3. 任何文本归一化必须记录原文、目标文案和规则 ID；
4. 公司字段不参与产品事实匹配。

## 7. Section 2：当前最大的结构性差异

### 7.1 标准答案结构

标准答案把 Section 2 拆分为：

- GHS 分类；
- GHS 标签要素；
- GHS 象形图；
- 信号词；
- 危险性说明；
- 防范说明；
- 物理和化学危险；
- 健康危害及其子项；
- 环境危害；
- 其他危害。

H/EUH/P 代码和完整语句按逻辑行保留。防范说明中的预防措施、事故响应、安全储存、废弃处置分别有清楚的分组边界。

### 7.2 当前结构

当前结果常见形态是：

2.1 GHS 危险性分类：
    分类结论 + 后续 2.2 标题和其他分类内容

2.2 GHS 标签要素：
    警示词 + 象形图 + 危险性说明 + 防范说明 + 全部 P 代码

2.3 其他危害：
    其他危害

已经确认的错误：

1. 2.1 值中混入 2.2 标题；
2. 2.2 值中混入警示词、象形图、危险性说明和防范说明；
3. P 分组标题和 P 语句没有投影到标准答案的独立逻辑边界；
4. 独立标签和独立值格的关系被压成一两个大值格；
5. 当前 Section 2 只有 4 行，而标准答案有 12 或 15 行。

### 7.3 根因

当前代码已经能从源中生成 ghs_classification、label_elements、signal_word、precautionary_statements 等 matchedRows，但 applyMatchResultToEditor 仍然把多个语义项目写入少数值格。也就是说，识别和语义匹配有结果，模板投影没有保持同样的粒度。

### 7.4 目标改造

Section 2 必须使用显式 slot projection：

source facts
    -> section2_routing
    -> ghs_classification
    -> label_elements
    -> pictogram
    -> signal_word
    -> hazard_statements
    -> precautionary_statements
    -> physical_hazards
    -> health_hazards
    -> environmental_hazards
    -> other_hazards
    -> fixed template slots
    -> omission and renumber

不能再使用“一个值格承载整段 Section 2”作为默认回退。

验收标准：

- H/EUH/P 代码和完整语句按完整逻辑行保留；
- P 分组标题不能进入标签列；
- 标签和值必须分离；
- H/P 行不消耗可见 2.x 编号；
- 源无值模板项目整行隐藏；
- 标准答案中独立成行的内容不能在当前结果中合并成一个大段落。

## 8. Section 3：三列结构稳定，但源名称保真不足

当前四个产品都保持了：

- 化学品名称、CAS、含量三列；
- 每个组分一行；
- 含量范围；
- N/A 或 CAS 值；
- 物理三列拓扑。

这部分符合旧 Skill 的 S3-001 和模板 mutation whitelist。

已确认差异：

PU-1002 的源文件和标准答案使用“水性聚氨酯树脂分散体”，当前结果使用“聚氨酯分散体”。

这不是换行或格式归一化，而是化学品名称被缩短。CAS 为 N/A 时，名称本身就是组分身份，不能用通用别名覆盖源名称。

优化要求：

1. 名称、CAS、含量绑定同一 source_fact；
2. 组分名称默认源文案；
3. 只有经过审核的专业词汇归一化才允许变化；
4. 三列值水平和垂直居中；
5. 组分一行，不能用摘要字符串替代。

## 9. Section 4：matchedRows 正确，最终值没有稳定投影

PU-1001 的源内容恰好和当前模板示例相近，因此当前结果看起来正确。这是一个危险假象。

PU-1002、PU-1003、PU-1004 的源值与标准答案不同，但当前结果仍出现模板示例类急救内容，例如立即脱掉所有被污染的衣物、禁止催吐、模板示例的眼睛冲洗和皮肤处理语句。

当前 matchedRows 已经能够得到源特定的急救内容，说明主要失败点在写入投影，而不是源事实识别。

当前 registry 的 Section 4 语义标签与 CN 模板历史标签不相同：

| 语义键 | registry 标签 | CN 模板实际标签 |
|---|---|---|
| symptoms | 4.5 最重要的症状和健康影响 | 4.1 一般措施 |
| ingestion | 4.4 食入 | 4.2 误服 |
| eye_contact | 4.2 眼睛接触 | 4.3 接触眼睛 |
| skin_contact | 4.1 皮肤接触 | 4.4 接触皮肤 |
| inhalation | 4.3 吸入 | 4.5 吸入 |

语义键是正确抽象，但必须有 CN 模板 profile 显式绑定到实际行，不能在写入阶段再靠标签文本、行号或剩余空值猜测。

每个 matchedRow 必须记录：

- template record id；
- target row index；
- target value cell id；
- before value；
- after value；
- source_fact id；
- 导出重载后的 after value。

只有导出重载后仍然相等，才算真正写入成功。

## 10. Section 5：内容可匹配，但语义换行丢失

当前结果和标准答案的主要差异有两类：

1. PU-1002、PU-1003、PU-1004 的消防值没有完全收敛到标准答案的源特定措辞；
2. 5.3、5.4 的独立句子被合并成单段。

标准答案保留：

燃烧时释放一氧化碳、二氧化碳、氮氧化物等。
在着火或爆炸情况下，不要吸进烟尘。

当前结果常见为：

燃烧时释放一氧化碳、二氧化碳、氮氧化物等。在着火或爆炸情况下，不要吸进烟尘。

5.4 的消防人员措施和污染灭火水措施同样被合并。

旧 MSDS Skill 要求源段落边界和语义句边界进入事实模型，不能在写入前统一 join 成一个字符串。建议为每条值增加 line_break_policy：

- verbatim_paragraph；
- semantic_sentence_break；
- code_per_line；
- compact_single_line。

Section 5 的建议：

- 5.1 完整句子可保持一行；
- 5.3 两个完整句子两行；
- 5.4 两个语义块两行；
- 禁止空段落、Tab、重复空格和单独斜杠。

## 12. Section 11：标准答案和当前结果差异最大

标准答案的 Section 11 通常只有：

1. Section 标题；
2. 源文件明确写出的产品级说明，例如“该产品无可用的毒理学研究。”。

当前结果保留约 15 行，包括急性毒性、经口/吸入/经皮、皮肤、眼睛、过敏、致突变、致癌、生殖毒性、11.8、11.9、11.10 等模板端点。

当前结果还出现：

- 空的经口/吸入/经皮子标签；
- 多个“无数据资料”值；
- 模板骨架被完整保留，即使源文件没有对应 endpoint。

旧 Skill 的独立开行规则要求：

- 产品级整体结论独立一行；
- 聚合物/组分层级独立一行；
- 组分研究引言独立一行；
- 每个测试端点独立一行；
- 源无端点时完整端点行隐藏；
- 不得把模板示例“无数据资料”当成源事实。

当前 Section 11 清理逻辑主要处理空一列行和少数旧示例文本，没有根据每一个 endpoint 的 source presence 完整删行。

改造顺序必须是：

source coverage
    -> endpoint presence manifest
    -> template endpoint alignment
    -> retain product-level availability statement
    -> hide unsupported endpoint rows
    -> hide unsupported middle sublabels
    -> renumber surviving rows

11.1 的经口/吸入/经皮以及 11.7 的生育力/致畸形/体外遗传毒性是模板拥有的子标签，只能写最终值格，不能因为源列表压缩而把值向上错位。

## 13. Section 12：产品级生态说明不能塞进端点

标准答案通常只保留源级说明：

该产品无可用的生态毒理学研究。

当前结果保留：

- 12.1 生态毒性：无数据资料 + 产品级说明；
- 12.2 持久性和降解性：无数据资料；
- 12.3 其他不利影响：无数据资料。

根因是 ecotoxicity 被直接写进 12.1，且没有按 endpoint presence 删除 12.2、12.3。

正确策略：

如果源只有产品级说明，Section 12 只保留独立说明行；

如果源存在生态毒性、降解性和其他不利影响，才分别写入对应端点，并把产品级说明作为独立说明行。

不能把产品级说明并入 12.1，也不能为了填满模板而保留模板“无数据资料”。

## 14. Section 15：法规命中了，但顺序和容量处理失败

标准答案顺序为：

1. 物质或混合物的相关安全、健康和环保法律法规；
2. 其它的规定；
3. 符合下列法规要求；
4. 危险化学品安全管理条例；
5. GB/T 16483；
6. GB 13690；
7. GB 30000.2-29；
8. GB 15258。

当前结果常见顺序为：

1. 其它的规定；
2. 符合下列法规要求；
3. 物质或混合物的相关安全、健康和环保法律法规；
4. 危险化学品安全管理条例；
5. GB/T 16483；
6. GB 13690；
7. GB 30000.2-29；
8. GB 15258 缺失。

当前 matchedRows 已经识别到 gb_15258，说明失败点是写入投影：

- safety_regulations 被当成普通法规值写到列表后面；
- 5 个法规项目写入到有限的剩余行；
- 容量不足时最后一个值被静默丢弃；
- 没有克隆完整样式行；
- 没有做 matchedRows 全量目标覆盖审计。

必须为 Section 15 建立独立行绑定，并在容量不足时按 mutation whitelist 克隆完整样式行。

## 15. 共性根因

### 15.1 语义注册表和模板结构不是同一套契约

registry 使用标准语义标签，CN 模板使用历史标签。没有 template profile 时，投影层不得重新靠标签文本猜测。

### 15.2 匹配模型和写入模型没有闭环

matchedRows 正确不代表最终 DOCX 正确。必须将每个 matchedRow 绑定到明确的模板行和值格，并在导出重载后验证。

### 15.3 模板示例清零范围不够精确

source-absent 项目应整行隐藏，不能只清值格。模板示例值绝不能因为匹配失败或槽位未命中而继续留在结果。

### 15.4 空值处理仍停留在清空值格

Section 11、12、15 要求的是语义项目级隐藏、独立说明保留和连续重排，而不是简单清空文本。

### 15.5 换行没有进入事实模型

源段落边界、句子边界、H/P 行边界、结构化字段边界都必须在事实阶段记录，不能在最后统一 join。

## 16. 结合旧 MSDS Skill 的统一优化架构

建议将当前链路固定为五层。

### 第一层：Source Coverage

- 文件格式；
- 表格、图片、嵌套表格和跨页表格；
- 每个 Section 的 source unit；
- unreadable、unmapped、ambiguous、conflict；

### 第二层：Fact Ledger

每条事实都有：

- fact_id；
- source_section；
- source_locator；
- source_text；
- normalized_value；
- source_unit_ids；
- evidence_type；
- line_break_policy；
- mapping_status。

### 第三层：Semantic Mapping

每条事实绑定：

- 目标 Section；
- semantic key；
- 归类依据；
- 取舍状态；
- 是否允许合并；
- 是否允许翻译或标准化；

### 第四层：Template Profile Projection

- templateId；
- templateHash；
- Section；
- semanticKey；
- targetRecordId；
- targetRowLocator；
- labelFingerprint；
- valueCellLocator；
- rowKind；

- lineBreakPolicy；
- omissionPolicy；
- insertionPolicy。

示例：

S4 / symptoms -> CN row 4.1 -> value column 1  
S15 / safety_regulations -> 独立说明行，而不是第一条法规数据行

### 第五层：Write and Reload Audit

3. 重新抽取 16 个 Section；

5. 比较标准答案 row presence；

不能只审查内存 editorEngine。

## 19. 最终判断

当前 MSDS Studio 已经具备不错的基础：

- 可以识别 16 个 Section；
- 可以生成语义匹配模型；
- Section 3 三列表格物理结构稳定；
- Section 8、9、10、13、14、16 部分结果接近标准答案；
- 可以执行一定的剪枝和连续编号。

但当前结果还不能作为接近标准答案的稳定生产链路，主要原因是：

1. 匹配统计没有覆盖最终模板投影；
2. Section 2 多槽语义被压缩；
3. Section 4/5 对产品差异没有可靠替换模板示例；
4. Section 11/12 没有按源存在性删除整行；
5. Section 15 法规槽位容量和顺序没有显式绑定；
6. S3 个别产品名称被泛化；
7. 句子换行没有作为事实属性传递到 Word；
8. .doc 入口和实际识别能力不一致。

最终应当采用以下单一事实链：

源文件事实
    -> 事实台账
    -> 语义映射
    -> 模板版本 profile
    -> 值格投影
    -> 空值项目隐藏/整行插入/连续编号
    -> 导出重载审计
    -> 标准答案 parity

不能再把“匹配到 77 个字段”当成完成标准。真正的完成标准是：

每一条源事实都有去向；每一个写入值都能回到源事实；每一个模板示例都被清除或明确保留；每一个标准答案结构差异都能由规则解释；导出后重新读取的 DOCX 与写入计划、模板结构和标准答案基准一致。
