## 1. 结论先行

当前确实存在可以释放的横向空间，而且这部分空间足以明显改善标签换行。空白的首要来源不是表格本身没有撑满，而是应用最外层的统一容器被固定在 `1920px`：当前浏览器 CSS 视口为 `2304px`，外层 `main.page-shell` 实际宽度为 `1920px`，左右各留下约 `180.6px` 的未使用空间。识别页和智能匹配页都受这个父容器约束。

智能匹配页还有第二层可回收空间：原始识别表和标准匹配表所在的 `.matching-col-scroll` 使用 `padding: 8px 10px`，每张表横向实际少用约 `20px`。在三屏同览模式下，当前原始表容器只有约 `427px`，表格本体约 `405px`；标准表容器约 `502px`，表格本体约 `480px`，这会把原本已经偏窄的标签列进一步压缩。

当前表格的列比例仍忠实沿用 DOCX 的 `gridWidthsTwips` 和单元格宽度：识别页 Section 9 的标签列约占 `34.782%`、实际宽度约 `304px`；智能匹配三屏模式下，原始表标签列约为 `141px`，标准表标签列约为 `172px`。因此，仅调整外层宽度就能改善换行；如果还要主动提高标签列占比，必须使用“仅用于网页阅读的自适应列宽策略”，不能把模板原始比例直接改写到匹配模型或导出 DOCX。

建议的安全方向是：

1. 宽屏下解除外层 `main.page-shell` 的 `1920px` 硬上限，把左右空白转给工作区。
2. 识别页优先把新增空间分给结构化识别表，原版式预览保留稳定的最低可读宽度。
3. 智能匹配页在三种模式下都把新增空间分给原始表/标准表，同时保留源文件预览的可读宽度。
4. 仅对“明确的两列标签-值表”执行自适应标签列宽；Section 3 三列成分表、单列正文、合并单元格和原版式预览不套用该规则。
5. 识别页和匹配页继续共用 `renderStructuredTable`，从同一套结构模型读取列信息，避免出现两个页面的标签和值位置规则分裂。

### 4.3 匹配页的第二层空白

`.matching-col-scroll` 的规则为：

```css

  padding: 8px 10px;
  overflow-y: auto;
  overflow-x: auto;
}
```

因此原始表和标准表各自损失约 `20px` 的横向表格宽度。这个间距不是模板结构，也不参与匹配；可在宽屏阅读模式中缩小为 `4px` 或仅保留边框所需的最小内边距。该调整可直接增加标签和值两列的可用宽度，且不触碰源数据和匹配规则。

## 6. 为什么不能直接把所有标签列改成 45% 或 50%

直接给所有 `.structured-table td:first-child` 设置更大比例会产生以下结构性风险：

1. Section 3 是三列成分表，第一列、CAS 列、含量列必须共同保持模板结构；把第一列统一扩大，会挤压 CAS 和含量列，破坏表头及数据对齐。
2. Section 2、11、13、15、16 存在单列正文或多段说明，单列行并不存在标签-值关系；把它们视为标签列会改变正文的阅读宽度和换行。
3. 有 `rowspan`、`colspan` 或合并单元格的表，列宽变化必须考虑被合并区域的总宽度，不能按单个首列单元格强行写入。
4. 原始识别表与标准模板表列比例不同，若只改其中一张，用户对照时会把显示差异误认为匹配错位。
5. `render-utils.js` 同时服务识别页、匹配页和模板编辑相关表格；全局覆盖会波及模板编辑器和已有的加粗/表头保护。
6. DOCX 导出和模板模型必须继续以源模板结构为准，网页显示用的列宽不能回写 `gridWidthsTwips`，也不能改变匹配槽位。

## 7. 推荐的实施方案（报告级方案，不是本次改动）

### 7.1 第一层：释放外层工作区宽度

把外层 `main.page-shell` 改成宽屏自适应，而不是继续固定在 `1920px`。推荐用“宽屏流式 + 超宽上限 + 窄屏断点”的策略：

- 宽屏：工作区使用 `calc(100vw - 32px)` 或等价的 `width: 100%`，不再留下 180px 级别的左右空白。
- 超宽：如确实需要避免内容过度摊开，可设置更高的上限（例如 `2400~2560px`），而不是当前的 1920px。
- 窄屏：保留现有 `max-width:1280px`、`820px` 的折叠和单列逻辑，不以宽屏方案破坏移动端。
- 识别页和匹配页都使用同一外层宽度预算，避免两个页面一宽一窄。

验收目标：在当前 `2304px` CSS 视口下，外层主工作区左右余量降到不超过 `16px`；在 `1920px` CSS 视口下不产生横向滚动；在 `1280px` 以下仍按现有响应式断点折叠。

### 7.2 第二层：重新分配识别页三列

识别页不应让新增宽度平均摊给预览和结构化表。建议：

- 侧栏继续保持约 `140px`，保证 16 个 Section 导航稳定。
- 结构化表列使用更高的弹性权重，例如 `minmax(0, 1.20~1.30fr)`。
- 原版式预览设置 `minmax(820px, 0.90~1.00fr)`，保证 DOCX 页面仍可读。
- `showPreview=false` 时，结构化表独占剩余宽度的逻辑保持不变。

在当前视口下，结构化表面板目标宽度建议至少达到 `1000px`；Section 9 的标签列在保留原比例的情况下应达到约 `350~380px`，先通过“面板变宽”解决大部分换行，再判断是否需要对少数双列表加宽。

### 7.3 第三层：重新分配匹配页三种模式

匹配页的每种模式要有明确的最小可读宽度：

- **原件对标：** 标准匹配表至少保留 `700~760px`，预览列至少 `850px`。
- **数据对标：** 原始表和标准表都建议至少 `700px`，不要让一侧低于另一侧的可读下限。
- **三屏同览：** 原始表建议至少 `520~600px`，标准表建议至少 `620~720px`，预览列保持 `700~850px`；如果视口不够，优先让三屏切换到两屏，而不是把表格压到一百多像素的标签列。

当前 `@media (max-width:1280px)` 已经将匹配模式切换为一列或两列，这是正确的退化方向；需要增加的是宽屏区间的分配，而不是取消窄屏断点。

### 7.4 第四层：回收匹配表内边距

在不改变表格边框和可读性的前提下，将 `.matching-col-scroll` 的横向内边距从 `10px` 降到 `4px` 左右，或在宽屏模式下使用专门的紧凑内边距类。必须保留可辨认的表格与面板间隔，不能直接让边框贴死标题栏。

该项属于纯 UI 空间回收，不接触识别结果、模板内容、匹配规则或导出结构。

### 7.5 第五层：建立网页阅读用的自适应标签列策略

只有满足以下条件的表格才允许自适应扩大标签列：

1. 结构为两列或可明确识别为“标签列 + 值列”。
2. 首列存在标签角色，另一列存在值角色。
3. 没有跨三列的表头、复杂合并或不确定的 `rowspan/colspan` 关系。
4. 当前列宽不足以容纳最长标签的序号槽、标签正文和单元格内边距。

建议算法如下：

```text
sourceLabelShare = DOCX 原始首列比例
labelNeed = 最长标签的实际测量宽度 + 序号槽 + 单元格内边距
valueNeed = 值列最小可读宽度
available = 当前网页表格宽度 - 边框和内边距

labelShare = clamp(
  max(sourceLabelShare, labelNeed / available),
  sourceLabelShare,
  min(48%, 1 - valueNeed / available)
)
```

实现时应把结果作为网页渲染层的 `data-layout`、CSS 变量或经过验证的 `colgroup` 宽度输出，不能修改：

- `gridWidthsTwips`；
- `cell.format.width` 的源数据；
- `runSmartMatching()` 的匹配槽位；
- `applyMatchResultToEditor()` 的写入关系；
- DOCX 导出使用的模板结构。

识别页、匹配页原始表和匹配页标准表都由同一个结构渲染器调用该策略；三屏对照时应采用相同的“标签列最小可读宽度”和“值列最小可读宽度”契约，避免两边仅因容器不同而出现完全不同的换行形态。

### 7.6 第六层：保留序号/标签槽位和文本格式规则

释放宽度不能破坏正在推进的全视图标签首字对齐治理。标签列变宽后仍必须保持：

- 固定序号槽和正文槽的共同起始线；
- 无序号标签使用空序号槽占位；
- 长标签续行在标签正文槽内悬挂对齐；
- 标签字体、值字体、表头字体仍由统一角色模型决定；
- Section 3 的三列表头不参与二列标签-值加宽规则；
- 单列说明行继续作为值/正文处理，而不是伪造一个标签列。

## 8. 验收与回归要求

本问题不能只靠现有语义测试判断完成，需要增加真实浏览器布局断言。建议至少覆盖：

### 8.1 宽度断言

- CSS 视口 `2304px`：主工作区左右空白不超过 `16px`。
- CSS 视口 `1920px`：不出现横向滚动，识别表和匹配表均完整可见。
- CSS 视口 `1440px`：识别页仍能保持标签和值可读，必要时按现有断点折叠预览。
- CSS 视口 `1280px` 及以下：匹配页按一列/两列退化，不强行保留三屏窄列。

### 8.2 结构和角色断言

- Section 3 三列表头列数、顺序、加粗/下划线和数据列不变。
- Section 2、11、13、15、16 的单列正文不被误判为标签-值二列。
- 合并单元格、`rowspan`、`colspan` 的总宽度关系不变。
- 原始识别表和标准匹配表的标签/值角色不因网页列宽调整改变。

### 8.3 视觉断言

- Section 9 的长标签换行数量下降，不能出现逐字竖排。
- Section 8 的子级标签、普通标签和值列不被挤成窄竖条。
- 多行标签续行仍与标签正文首字对齐。
- 识别页和匹配页使用同一套标签字体和值字体规则。
- DOCX 原版式预览只作为预览，不被结构化表网页列宽策略改写。

### 8.4 数据安全断言

- 调整浏览器宽度后，识别记录文本完全不变。
- 重新匹配前后，匹配计数、映射键、审阅标记不变。
- 导入编辑模块后，模板列结构、加粗标签和可编辑值位置不变。
- 导出 DOCX 前后的源模板比例和合并关系不被网页显示层写回。

## 9. 当前自动化测试结果与覆盖缺口

本次未修改代码，现有测试均通过：

- `npm run test:smoke`：通过，内嵌模板和样例文件验证干净。
- `node tests/test_ui_alignment_and_table_headers.mjs`：通过，现有双槽结构、表头、垂直居中和单列正文角色断言通过。
- `node tests/test_full_problem_inventory.mjs`：通过，42 项问题清单为 0 缺陷。

这些测试主要验证语义、角色、模板残留和静态渲染契约，没有覆盖本报告的核心几何问题：外层最大宽度、宽屏空白、各匹配模式实际列宽、表格容器内边距、在多个 viewport 下的换行数量。因此“自动化测试通过”不能等同于“宽屏空间已被充分利用”，需要增加浏览器级几何测试后才能验收。

## 10. 风险边界和禁止做法

### 可以做

- 放宽外层页面工作区；
- 重新分配识别页/匹配页的面板比例；
- 减少匹配表容器的横向装饰内边距；
- 对明确的两列标签-值表执行网页显示层自适应列宽；
- 用共同的渲染器和共同的最小宽度契约同步识别表、原始表和标准表。

### 不应直接做

- 全局把所有首列设为固定 `45%` 或 `50%`；
- 修改 `gridWidthsTwips`、模板 DOCX 的列宽或合并关系来解决网页换行；
- 让网页显示层的列宽结果回写匹配模型或导出 DOCX；
- 为了保留三屏而把原始表/标准表压到 `141~172px` 的标签列；
- 对单列正文和 Section 3 三列表格套用二列标签-值规则；
- 只依赖静态测试，不做至少一个宽屏和一个窄屏的真实 DOM/截图验收。

## 11. 最终判断

本次调查确认：用户截图中两侧的大块空白是真实可用的布局预算，首要根因是 `main.page-shell` 的 `1920px` 最大宽度；智能匹配表自身还存在每侧 `10px` 的额外内边距。当前结构化表列比例本身来自源模板，不能简单粗暴地全局放大首列。最安全、最有效的实施顺序是：

```text
释放外层宽度
    -> 重新分配识别页/匹配页面板
    -> 回收匹配表容器内边距
    -> 仅对明确二列标签-值表做自适应标签列
    -> 在 2304/1920/1440/1280 等视口做结构、视觉、数据回归
```

这条路径能够利用现有空白，降低标签换行和伪竖排风险，同时保持识别结果、模板结构、匹配规则、映射关系、加粗标签保护和 DOCX 导出边界不被网页布局优化破坏。

## 12. Section 5 续行首字未与第一行中文首字对齐（本次补充审计）

### 12.1 用户截图中的问题已被运行时坐标确认

用户给出的 Section 5 截图所表达的要求是：一个标签因为列宽不足而换成两行时，第二行的第一个中文字符必须与第一行的第一个中文字符处在同一条垂直线上。当前实现没有达到这个要求。

本次在智能匹配“三屏同览”模式定位 Section 5，分别测量原始识别表和标准匹配表的标签单元格、序号槽、正文首行和续行文字范围。结果如下：

| 表格 | 标签 | 第一行中文首字 X | 第二行首字 X | 错位量 |
|---|---|---:|---:|---:|
| 原始识别表 | 5.1 合适的灭火剂： | 262.14px | 217.35px | -44.79px |
| 原始识别表 | 5.2 不合适的灭火剂： | 262.14px | 217.35px | -44.79px |
| 原始识别表 | 5.3 物质或混合物的特殊危害： | 262.14px | 217.35px | -44.79px |
| 原始识别表 | 5.4 消防预防措施和保护设备： | 262.14px | 217.35px | -44.79px |
| 标准匹配表 | 5.2 不合适的灭火剂： | 761.77px | 716.98px | -44.79px |
| 标准匹配表 | 5.3 物质或混合物的特殊危害： | 761.77px | 716.98px | -44.79px |
| 标准匹配表 | 5.4 消防预防措施和保护设备： | 761.77px | 716.98px | -44.79px |

`44.79px` 正好等于当前序号槽的实际宽度。也就是说：

```text
第一行： [5.1  ] [合适的灭火剂：]
第二行： [合适的灭火剂：]
         ^ 回到了单元格左边缘，而不是正文槽的起始线
```

这不是截图缩放导致的错觉，而是浏览器文本 Range 的真实布局坐标。原始识别表第一列标签单元格宽约 `161.40px`，标准匹配表第一列标签单元格宽约 `166.95px`；在这两个窄列中，5.1~5.4 的标签都会出现续行回左问题。

### 12.2 运行时 DOM/CSS 证据

源码原本声明：

```css
.label-line-grid {
  display: grid !important;
  grid-template-columns: var(--sequence-width, 2.8rem) minmax(0, 1fr) !important;
  column-gap: 0.35rem !important;
}
```

但运行时实际计算结果为：

| 节点 | 期望 | 实际计算值 |
|---|---|---|
| `.label-line-grid` | `display: grid` | `display: block` |
| `.label-line-grid` | 序号槽 + 正文槽 | `grid-template-columns` 虽保留，但由于不是 grid 容器而不起作用 |
| `.sequence-run` | 序号槽第一列 | 普通 `inline-block` 流 |
| `.label-text-slot` | 正文槽第二列 | 普通 `inline` 流 |

覆盖关系来自 `web/src/styles.css` 的以下规则：

```css
.structured-table td:first-child .label-parent-row,
.structured-table td:first-child .label-child-row,
.structured-table td:first-child .label-title-row,
.label-parent-row,
.label-child-row,
.label-title-row {
  display: block !important;
}
```

`renderParagraph()` 输出的标签容器同时带有两个 class：

```html
<div class="label-line-grid label-parent-row">
  <span class="sequence-run">5.1  </span>
  <span class="label-text-slot">合适的灭火剂：</span>
</div>
```

由于 `.structured-table td:first-child .label-parent-row` 的选择器特异性高于单独的 `.label-line-grid`，即使两边都写了 `!important`，前者仍然把标签容器强制成 `display:block`。此时两个 `span` 退化为普通行内流，第一行先放序号再放正文，第二行重新从父级左边开始排版，于是续行首字向左错开一个序号槽。

### 12.3 影响范围

这个覆盖规则影响所有通过 `renderParagraph()` 输出 `label-line-grid label-parent-row` 的窄标签列，至少包括：

- DOCX 识别页的 Section 5、Section 8、Section 9、Section 10、Section 12、Section 14 等两列结构；
- 智能匹配页的原始识别表；
- 智能匹配页的标准匹配表；
- 所有未来加载的、带序号且发生自动换行的标签。

它同时解释了用户截图中 5.1、5.2、5.3、5.4 的红框现象：第一行有序号，第二行却从标签格的最左边开始，形成“序号在第一行、文字在第二行回退”的结构错位。

这与“标签列宽度不足”是两个叠加问题：

1. 三屏同览下标签列确实过窄，容易触发换行；
2. 一旦换行，当前 CSS 又让续行回到单元格左边，破坏了首字垂直对齐。

因此，仅仅继续扩大标签列，不能彻底解决问题；即使列宽暂时足够，后续更长模板标签仍然会重新触发同一错位。

### 12.4 当前自动化测试为什么没有发现

现有 `web/tests/test_ui_alignment_and_table_headers.mjs` 只检查：

- 生成的 HTML 是否包含 `class="label-line-grid"`；
- CSS 是否存在 `.label-line-grid` 声明；
- 是否没有旧的 `vertical-align: top !important` 暴力覆盖；
- 静态样式字符串和模型结构是否存在。

它没有启动真实浏览器去检查：

- `getComputedStyle(.label-line-grid).display` 是否为 `grid`；
- `.label-text-slot` 是否真正位于 grid 第二列；
- 第一行与续行文字 Range 的 `x` 坐标是否一致；
- 原始识别表和标准匹配表是否都满足同一坐标契约。

所以现有静态测试可以通过，但用户在页面上仍然看到续行首字回左。这是一个典型的“静态结构存在、运行时布局失效”的测试覆盖缺口。

### 12.5 修复设计要求（补充到上一次宽度方案）

本问题修复必须和上一报告的“释放宽度、减少换行”方案同时设计，但不能用扩大列宽代替结构修复。

#### 必须满足的结构规则

1. `.label-line-grid` 在标签首列中运行时必须保持 `display: grid`。
2. `.label-line-grid` 必须有固定序号槽和正文槽；正文槽必须从统一的正文起始线开始。
3. `.label-text-slot` 应明确作为第二个 grid item，建议设置 `display: block; grid-column: 2; min-width: 0;`。
4. `.sequence-run` 或 `.sequence-slot` 应明确位于第一槽，不能依赖普通 inline 流的自然换行。
5. 自动换行和显式换行的每一行，首字 X 坐标都必须与正文槽左边缘相同。
6. 无序号标签使用空序号槽时，第二行也必须与其他标签的正文起始线一致。
7. 不得通过给续行额外添加 `padding-left` 的方式临时补偿；那会破坏有序号、无序号和多位序号之间的统一几何契约。

#### CSS 修复优先级

推荐优先排除网格容器：

```css
.structured-table td:first-child .label-parent-row:not(.label-line-grid),
.structured-table td:first-child .label-child-row:not(.label-line-grid),
.structured-table td:first-child .label-title-row:not(.label-line-grid) {
  display: block !important;
}

.structured-table td:first-child .label-line-grid {
  display: grid !important;
  grid-template-columns: var(--sequence-width, 2.8rem) minmax(0, 1fr) !important;
}

.structured-table td:first-child .label-line-grid .label-text-slot {
  display: block !important;
  grid-column: 2 !important;
  min-width: 0 !important;
}
```

实际改代码时还需检查模板编辑器的标签输出，确保锁定态和编辑态没有再把双槽容器降级成普通 `div`。这段 CSS 只是报告中用于说明修复方向的示例，不代表本次已经修改代码。

#### 必须新增的浏览器级验收

在识别页和智能匹配页分别验证 Section 5、Section 8、Section 9、Section 10、Section 11：

```text
computedStyle(labelGrid).display === "grid"
computedStyle(labelTextSlot).display === "block"
firstLineX(labelTextSlot) == continuationLineX(labelTextSlot) ± 1px
```

至少要对智能匹配三屏模式的原始表和标准表同时断言。对 Section 5 当前实测数据，修复后应满足：

- 原始识别表第一行与第二行均约为 `262.14px`；
- 标准匹配表第一行与第二行均约为 `761.77px`；
- 允许浏览器抗锯齿或小数布局产生不超过 `1px` 的误差；
- 不能再出现 `217.35px` 或 `716.98px` 这种回到单元格左边缘的续行坐标。

此外还要验证：

- 标签内容没有被截断或重复；
- 序号没有被当成正文值；
- Section 3 三列成分表不套用二列续行规则；
- 单列正文不被转换成标签网格；
- 原始识别表和标准匹配表采用同一套首字对齐契约；
- 增大页面宽度后，标签可以少换行，但发生换行时首字仍然严格共线。

### 12.6 本次补充结论

用户提出的“第二行首字必须跟第一行中文首字对齐”是当前页面中已经确认存在的真实缺陷，根因是 `.label-line-grid` 被 `.structured-table td:first-child .label-parent-row` 的高特异性 `display:block !important` 覆盖。该问题与外层宽度不足相互叠加，属于必须单独修复并单独验收的结构性 UI 缺陷。

上一报告关于释放页面空白、放宽标签列的建议仍然成立，但实施顺序必须调整为：

```text
先恢复 label-line-grid 的真实 Grid 布局
    -> 保证续行首字与正文首字共线
    -> 再释放外层空白和扩大标签列
    -> 最后用浏览器坐标回归验证所有视图
```

否则只会得到“标签少换行，但一旦换行仍然错位”的不完整修复。
