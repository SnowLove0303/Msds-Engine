# MSDS 识别结果序号显示问题研究报告

## 一、报告目的

本报告针对 PU-2341E MSDS DOCX 在 MSDS Studio 页面中的“序号丢失”现象进行定位，重点核对：

1. 源 DOCX 是否实际包含 Section 1、Section 7 的序号；
2. 识别模块是否抽取到了自动编号；
3. 网页结构化识别结果是否生成了序号；

## 三、最终结论

### 3.1 当前网页结构化识别结果并没有丢失 Section 1、Section 7 的序号

当前页面已经加载该 PU-2341E 文件，文件卡片显示：

- 文件名：`PU-2341E msds_CN 冠志.docx`
- 识别状态：`16/16`

网页结构化结果中实际存在以下序号：

Section 1：

- `1.1 产品名称：`
- `1.2 产品使用建议和使用限制：`
- `1.3 供应商信息：`

Section 7：

- `7.1 安全操作防范：`
- `7.2 安全储存条件：`

这些序号不是浏览器辅助功能树虚构出来的文本，而是结构化结果表格中的独立序号节点。

### 3.2 当前页面检测到的是“序号视觉上不明显”，不是“识别结果中没有序号”

浏览器 DOM 检查结果显示，序号节点具有以下状态：

| 检查项 | Section 1 | Section 7 |
|---|---:|---:|
| 序号节点数量 | 3 | 2 |
| 序号文本 | `1.1`、`1.2`、`1.3` | `7.1`、`7.2` |
| `display` | `inline-block` | `inline-block` |
| `visibility` | `visible` | `visible` |
| `opacity` | `1` | `1` |
| 文字颜色 | `rgb(32, 42, 51)` | `rgb(32, 42, 51)` |
| 是否与标签同一单元格 | 是 | 是 |

序号位于标签单元格的最左侧，和标签处于同一文本流中。当前浏览器测得 Section 1 的 `1.1` 节点左边缘约为 `505.61px`，所在标签单元格左边缘约为 `504.16px`；Section 7 的 `7.1`、`7.2` 也使用同样的布局方式。

因此，当前结构化表格的实际状态是：

> 序号已经生成、已经进入 DOM、已经处于可见状态，但紧贴表格左边界，视觉尺寸和边界间距不足，在当前页面缩放比例下容易被误认为没有显示。

### 3.3 源 DOCX 的序号主要是 Word 自动编号，不是普通文本

源文件中的 `1.1`、`1.2`、`1.3`、`7.1`、`7.2` 并不全部存在于 `<w:t>` 文本节点中。

源 DOCX 的 Word XML 使用了：

- `w:pPr`
- `w:numPr`
- `w:ilvl`
- `w:numId`
- `word/numbering.xml`

例如：

- Section 1 的“产品名称：”段落带有 `ilvl=1`、`numId=1`；
- Section 7 的“安全操作防范：”段落带有 `ilvl=1`、`numId=6`；
- 对应编号模板使用 `%1.%2` 形式生成多级编号。

也就是说，Word 在打开文档时根据 `numbering.xml` 动态显示 `1.1` 或 `7.1`，而不是简单从文本中读取一个已经写死的字符串。

这与中间结构化识别表格不是同一套渲染路径：

- 中间区域：应用自定义结构化表格和 `.sequence-run`；
- 右侧区域：第三方 DOCX 预览组件重新解释 Word XML；
- 右侧异常不能反向证明中间识别数据丢失。

## 五、识别模块层分析

### 5.1 识别模块读取到的普通文本不包含自动编号

`msds_table_search.py` 的基础识别结果主要通过 `python-docx` 读取单元格文本和段落文本。

对 Section 1，基础单元格文本类似：

- `产品名称：`
- `中文名称：`
- `化学品分类：`
- `产品使用建议和使用限制：`
- `供应商信息：`

对于 Section 7，基础单元格文本类似：

- `安全操作防范：`
- `安全储存条件：`

自动编号不是普通文本，因此不会天然出现在 `cell.text` 或 `<w:t>` 内容中。

### 5.2 基础识别模型虽然保留了部分段落格式证据，但没有完整暴露编号参数

基础识别结果保留了段落的直接 OOXML 属性，但当前 `numPr` 的直接属性结构没有把 `numId`、`ilvl` 作为一个可直接用于还原序号的稳定字段输出。

因此，如果后续流程只读取：

```text
cell.text
```

而不读取：

```text
paragraph.pPr.numPr
word/numbering.xml
```

就会出现：

> 标签文字存在，但自动编号看起来丢失。

### 5.3 这不是源文件没有序号

源文件的序号来源于 Word 编号定义，不应通过“标签文字是否以 1.1 开头”来判断源文件是否有序号。

正确判断顺序应为：

1. 先检查段落是否存在 `w:numPr`；
2. 根据 `numId` 找到 `numbering.xml` 中的编号定义；
3. 根据 `ilvl` 找到多级编号层级；
4. 根据 `lvlText` 和计数状态生成编号；
5. 再将生成的编号与原始标签文本组合。

## 六、网页识别与渲染链路分析

### 6.1 网页识别引擎已经实现自动编号解析

`web/src/docx-engine.js` 已经存在编号定义解析逻辑：

- 读取 `word/numbering.xml`；
- 建立 `abstractNum`、`numId`、`ilvl` 的映射；
- 读取 `lvlText` 和编号格式；
- 维护不同 `numId` 的计数器；
- 生成 `numberingText`；
- 将编号拼接到段落文本和标签候选中。

相关实现位置：

- `parseNumberingDefinitions`：解析编号定义；
- `numberingTextForParagraph`：根据段落 `numPr` 生成编号；
- `parseParagraph`：将编号保存为 `numberingText`；
- `cellRole`：把自动编号纳入标签识别；
- `normalizedSequence`：统一序号格式并生成显示文本。

### 6.2 网页结构化渲染已经把序号和标签放在同一列

`web/src/main.js` 的 `renderParagraph` 对数据行执行以下逻辑：

1. 从段落或单元格读取标准化序号；
2. 生成 `<span class="sequence-run">`；
3. 保留标签原始文本；
4. 将序号节点和标签节点放在同一个结构化单元格中。

当前 DOM 的实际结构等价于：

```html
<div class="structured-cell-copy">
  <div>
    <span class="sequence-run">1.1&nbsp;&nbsp;</span>
    <span>产品名称：</span>
  </div>
</div>
```

Section 7 的结构同样是：

```html
<span class="sequence-run">7.1&nbsp;&nbsp;</span>
<span>安全操作防范：</span>
```

### 6.3 当前 CSS 没有把序号隐藏

当前序号样式为：

```css
.sequence-run {
  display: inline-block;
  white-space: pre;
  font-weight: 700;
  margin-right: 0.15rem;
}
```

当前 DOM 检查结果也确认：

- `display: inline-block`；
- `visibility: visible`；
- `opacity: 1`；
- 文字颜色为深色；
- 序号与标签处于同一个单元格。

因此，目前不能把问题定性为“CSS 使用 `display:none` 导致序号完全不渲染”。

### 6.4 当前问题更接近视觉布局和可见性问题

当前序号被放置在标签单元格最左边，单元格只有约 `1px` 左内边距，序号本身的宽度较窄。

这种布局会带来以下视觉风险：

- 序号贴着表格左边线，和边框视觉混在一起；
- 页面缩放或截图缩小时，`1.1`、`7.1` 等短文本不容易被识别；
- 标签为粗体时，标签本身视觉重量明显高于序号；
- 序号和标签没有固定的独立对齐槽位；
- 不同序号长度（`1.1`、`9.19`、`10.1`）会导致标签起始位置不完全稳定；
- 右侧原版式预览的编号异常会进一步造成用户对识别结果的怀疑。

## 七、问题分层结论

| 层级 | 是否存在问题 | 结论 |
|---|---|---|
| 源 DOCX | 否 | 源文件存在 Word 自动编号，序号不是普通文本而是编号定义生成 |
| 基础文本识别 | 有潜在风险 | 只读取普通文本时天然无法得到自动编号 |
| 网页编号解析 | 当前已实现 | `numbering.xml`、`numPr`、`ilvl` 已被解析并生成 `numberingText` |
| 结构化结果数据 | 当前未发现丢失 | Section 1、Section 7 的序号节点均存在 |
| 结构化结果 DOM | 当前未发现隐藏 | 序号节点 `display:inline-block` 且 `visibility:visible` |
| 结构化结果视觉呈现 | 存在可疑问题 | 序号太靠左、太不突出，用户视觉上容易认为丢失 |
| 右侧原版式预览 | 存在独立异常 | 自动编号在预览组件中出现 `.1`、`0.1` 等异常形态 |
| 序号与标签同列 | 已满足 | 序号和标签位于同一个标签单元格 |

## 八、根因树

```text
用户看到“序号丢失”
├─ 根因 A：Word 自动编号不是普通文本
│  ├─ 序号来自 w:numPr + numbering.xml
│  ├─ 直接读取 cell.text 得不到 1.1 / 7.1
│  └─ 基础识别链路若不补编号，就会出现数据层缺号
│
├─ 根因 B：不同识别路径对自动编号处理不一致
│  ├─ 基础 Python 识别模块主要输出普通文本
│  ├─ Web docx-engine 已补充 numberingText
│  └─ 导出 JSON、结构化表格、原版式预览可能看到不同结果
│
├─ 根因 C：结构化表格序号的视觉呈现不够稳定
│  ├─ 序号在单元格最左边
│  ├─ 左内边距极小
│  ├─ 没有固定的序号列/序号槽位
│  ├─ 序号长度变化时标签起始位置不稳定
│  └─ 缩放后短序号不醒目
│
└─ 根因 D：原版式预览是另一条渲染链
   ├─ DOCX 预览组件重新解释自动编号
   ├─ 自动编号出现 .1 / 0.1 等视觉异常
   └─ 用户容易把预览异常误认为识别结果异常
```

## 十一、建议的修复方向

### 11.1 建立统一的编号事实模型

不要让不同模块分别猜测序号。每个段落应统一保存：

- `rawText`：源文本，不含自动编号；
- `numberingText`：依据 `numbering.xml` 解析得到的编号；
- `normalizedSequence`：统一格式后的显示编号；
- `sequenceSource`：`explicit_text` 或 `word_numbering`；
- `numId`；
- `ilvl`；
- `numberingDefinition`；
- `sequenceConfidence`。

这样可以区分：

- 源文本本身写了 `9.17`；
- Word 自动编号生成了 `7.1`；
- 页面为了标准化格式展示了 `7.1`。

### 11.2 将序号显示从普通文本流改为稳定的双槽位布局

序号和标签虽然仍属于同一标签列，但显示上应采用稳定结构：

```text
标签单元格
├── 序号槽位：固定宽度、右对齐
└── 标签槽位：统一左起始位置
```

这样可以保证：

- `1.1`、`7.1`、`9.19`、`10.1` 的标签首字始终垂直对齐；
- 序号不会贴到表格边线；
- 序号不会因长度变化挤压标签；
- 序号仍然与标签保持同一列；
- 不需要额外绘制独立表格列。

### 11.3 结构化结果和原版式预览分别验证

验收时必须分开检查：

1. 结构化识别结果：看序号事实、序号 DOM 和标签对齐；
2. 原版式预览：看 DOCX 预览引擎是否准确还原 Word 自动编号；
3. 导出 JSON：看 `numberingText` 是否完整保存；
4. 导出 DOCX：看源文件编号 XML 是否未被破坏。

不能用右侧原版式预览的显示结果替代结构化识别结果判断，也不能只看 DOM 文本而不做截图视觉检查。

### 11.4 增加回归测试样本

至少应覆盖以下断言：

- Section 1：`1.1`、`1.2`、`1.3`；
- Section 3：`3.1`、`3.2`；
- Section 7：`7.1`、`7.2`；
- Section 9：`9.1` 至 `9.19`；
- Section 14：拆分后每一行的源编号与标签均保留；
- 结构化结果中每个序号节点可见；
- 序号与标签的起始位置满足固定对齐误差；
- 基础 JSON 中 `numberingText` 不为空；
- 显式编号和自动编号不会重复拼接；
- 标题行不重复注入序号；
- Section 15 不错误注入序号。

## 十二、验收标准

### 数据层

- 自动编号必须从 `numbering.xml` 解析，而不是依赖肉眼或字符串猜测；
- 所有自动编号段落必须有可追踪的 `numId`、`ilvl` 和生成结果；
- `cell.text` 缺少编号时，不得被当成“源文件没有编号”；
- 源编号和页面标准化编号必须能区分。

### 结构化表格层

- Section 1 显示 `1.1`、`1.2`、`1.3`；
- Section 7 显示 `7.1`、`7.2`；
- 序号与标签处于同一列；
- 序号在截图中肉眼可见；
- 标签首字在所有数据行中垂直对齐；
- 长序号与短序号不改变标签首字位置；
- 序号不会被左边框遮挡，也不会被表格滚动区域裁剪。

### 原版式预览层

- 原始 Word 自动编号不应出现 `0.1`、`.1` 等错误显示；
- 原始预览和结构化结果应至少在编号语义上保持一致；
- 预览异常必须显示为预览兼容性问题，不能混同为识别结果缺失。

## 十三、研究结论摘要

本次核对结果可以明确分成两句话：

1. **当前网页中间的结构化识别结果，Section 1 和 Section 7 的序号已经被识别并生成，DOM 中可以确认 `1.1/1.2/1.3` 和 `7.1/7.2` 均存在。**
2. **用户肉眼看到的“序号没有显示”，主要是序号在表格左边界处显示过于贴边、不突出，以及右侧原版式预览存在另一套自动编号显示异常共同造成的视觉和认知问题。**

同时，基础识别模块本身仍存在自动编号没有作为独立字段统一输出的结构性风险。后续真正修复时，必须同时处理：

- 自动编号事实提取；
- 统一数据模型；
- 结构化结果的序号槽位布局；
- 原版式预览的编号兼容性；
- JSON、网页、编辑器和导出链路的一致性。
