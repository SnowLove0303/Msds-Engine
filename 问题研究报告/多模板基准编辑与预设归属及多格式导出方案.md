## 1. 产品判断与需求边界

用户指出的问题成立。当前导出把“可选择英文模板”错误地等同于“已经存在用户完成的英文稿”。只有中文工作内容时，不能因为英文模板和英文预设存在，就生成一份声称来自用户编辑的英文文件。

新的主结构应为：

```text
Template registry
  -> Workspace / source record
       -> Baseline A -> saved draft A -> presets owned by A
       -> Baseline B -> saved draft B -> presets owned by B
       -> Baseline C -> saved draft C -> presets owned by C
  -> Selected ready drafts and their own presets
  -> Word / PDF
  -> One ZIP download
```

本次需求中的“中英文切换”是当前两种基准的实际使用场景；系统能力应命名为“模板基准切换编辑”。中文、英文、客户名、发布主体都可以是模板元数据或显示名称，不能作为全局写死的分支和归属键。

需要实现的行为：

1. 每个工作项目中，同一模板基准拥有独立的编辑稿；A 切到 B 再回 A，恢复 A 已编辑内容。
2. 编辑稿能持久保存，刷新或重启后可恢复；不能只有运行时对象引用。
3. 预设创建前确定所属模板基准；列表、编辑、复制和应用均以该归属为前提。
4. 尚未编辑完成的基准及其预设不得进入导出计划。
5. 完成多个基准后，在一次导出中按基准分组勾选基础稿或该基准的预设版本，选择 Word、PDF 或两者。
6. 新增第三个基准，即使它与某个旧基准都是中文，也能独立工作，不需要增加“第三语言”或“第三公司”代码分支。

本次先交付代码调查与方案。自动翻译、跨基准自动同步内容不作为本次能力的前提，也不会在方案里把两者伪装成已经存在。

## 2. 当前代码事实与缺陷

本次调查的是安装目录当前源码；此前 UI 报告中的行号和实现已发生变化，应以本报告记录的函数和代码快照为准。

### 2.1 模板目录只有两个静态映射，没有通用注册模型

[main.js](<F:/App Location/Guanzhi Tong/Skill/MSDS-Engine/web/src/main.js:72>)：

```js
const TEMPLATE_OPTIONS = {
  'CN 冠志': '正式模板_MSDS_CN_冠志(1).docx',
  'EN 冠志': '正式模板_MSDS_EN_冠志(1).docx',
};
```

当前物理模板文件也只有这两份。预设 targetTemplate 里出现的 CN 国彩、EN 国彩主要是历史输出配置，并不对应两份另外注册的模板资产。

问题不是只有两个模板，而是模板显示名被同时用于资源定位、语言推断、预设目标与编辑状态。用户改名、增加同语言模板或更换模板文件时，很难判断哪些关联仍然有效。

### 2.2 主稿编辑状态是单例，切换明确丢弃修改

[loadEditorTemplate](<F:/App Location/Guanzhi Tong/Skill/MSDS-Engine/web/src/main.js:3650>)：

```js
if (state.editor.dirty &&
    !window.confirm('当前工作副本有未导出修改，切换模板会丢弃这些修改。继续吗？')) return;
const engine = await fetchTemplate(name);
state.editor.template = name;
state.editor.engine = engine;
state.editor.dirty = false;
```

state.editor 只有一个 engine 和一个 normalEngine，没有按模板基准索引的草稿集合。templateBufferCache 缓存的是原始模板文件字节；repoEngineMemoryCache 按记录缓存匹配/识别引擎，均不能替代每个基准的持久编辑稿。

智能匹配“投入编辑器”、导入 DOCX、重载模板、预设编辑等入口也直接赋值 state.editor.engine。改切换下拉框这一处不足以建立可靠草稿体系。

### 2.3 导出清单通过语言和主体做笛卡尔积

[computeExportTargets](<F:/App Location/Guanzhi Tong/Skill/MSDS-Engine/web/src/main.js:529>) 读取 langCn、langEn、includeGuanzhi、includeGuocai，再遍历语言、主体、格式组合。自定义预设还被循环套入每一个已选语言。

这段逻辑检查“用户勾选了哪些语言”，没有检查“对应基准是否存在已完成的编辑稿”；也没有检查自定义预设与某个基准的归属关系。

因此 A 预设可能被套到其他基准；新增同语言基准也不能独立出现在这套二维 UI 中。

### 2.4 英文导出没有读取独立英文稿

[executeUnifiedExport](<F:/App Location/Guanzhi Tong/Skill/MSDS-Engine/web/src/main.js:3971>) 的英文路径：

```js
doc = await fetchTemplate('EN 冠志');
const preset = state.editor.presets.find(p => p.id === 'preset_guanzhi_en');
if (preset) applyPresetPriorityOverlay(baseEngine, preset, doc);
```

其中 baseEngine 是当前唯一主稿。applyPresetPriorityOverlay 抽取它的语义字段快照，直接应用到目标引擎；没有翻译行为，没有独立英文稿检查。fetchTemplate 失败还会退回当前主稿字节，进一步掩盖目标基准未准备的问题。

当当前主稿本身是英文时，中文冠志分支直接使用 baseEngine，也存在“中文命名对应英文实际内容”的反向风险。这是代码分支推导，未在浏览器执行该反向用例。

### 2.5 原始字节不能代表编辑后的工作稿

[engineBuffer](<F:/App Location/Guanzhi Tong/Skill/MSDS-Engine/web/src/main.js:229>) 返回 engine.originalBytes；[loadDocx](<F:/App Location/Guanzhi Tong/Skill/MSDS-Engine/web/src/docx-engine.js:1127>) 的第二参数只是来源名称，不会根据名称载入另一个模板。

exportArrayBuffer 才会把当前 documentXml、页眉页脚、图片及关系写回 DOCX 包。

若只保存原始字节或只保存语义字段，可能丢失用户新增/删除的行、说明、图像或其他结构变化。因此草稿应保存完整当前 DOCX 快照，并附带 UI 元数据；语义快照只用于差异定位，不承担整份稿件的唯一存储。

### 2.6 预设没有可靠的基准外键，前后端还不同步

当前默认预设包含 language、entity、targetTemplate；自定义预设创建主要接收 targetTemplate。数据库 presets 表没有 baseline_id，也没有对应模板注册表。

此外，PresetStore.fetchPresetsFromApi 期待 data.presets 和 snake_case 字段；API 实际返回 { success: true, data: [...] }，列表对象使用 camelCase。此响应格式不匹配会让前端加载不到 API 预设后继续使用本地列表。

PresetStore.savePresets 主要写 localStorage；API CRUD 写 SQLite。不能只往一个地方新增 baselineId，另一个地方仍按旧结构运行。

### 2.7 已有 PDF 能力，但失败处理会导致交付不完整

[PDF 转换器](<F:/App Location/Guanzhi Tong/Skill/MSDS-Engine/web/src/pdf-converter.js:66>) 使用 LibreOffice；API 已有 /api/msds/convert-pdf-batch，前端可提交生成后的 DOCX。

当前 executeUnifiedExport 在转换接口失败时主要写 console.warn，随后继续组装已得到的文件。选择 Word+PDF 时，PDF 缺失也可能只交 Word 并提示成功。

本机确实检测到 LibreOffice 控制台程序；这不代表已验证所有页面的 PDF 布局或成功转换。探测逻辑还偏 Windows，对 PATH 中的 soffice 和容器环境支持不完整。

### 2.8 旧入口和 API 也必须纳入调整

除了统一导出，还保留 executeBatchPresetExport、exportDocx，以及服务端 /api/msds/export。控制器中同一路由的 POST 处理出现两段，应在实施时核对分支可达性并收敛。

服务端 sessions 是内存 Map，一个 session 只有一个 editorEngine。单改浏览器 UI 会留下 API 绕过归属检查、应用预设到错误主稿或重启丢稿的问题。

## 4. 核心数据模型

### 4.1 模板基准 TemplateBaseline

建议字段：

```ts
interface TemplateBaseline {
  id: string;                 // 稳定 ID，不用显示名称、语言或文件路径作 ID
  displayName: string;        // UI 原样显示，可改名
  assetId: string;            // 本地受管模板资源
  revision: string;           // 模板资产/结构版本
  contentHash: string;
  fieldSchemaVersion: string;
  defaultFileNamePattern: string;
  metadata?: Record<string, unknown>; // 可选语言等描述信息
  archived: boolean;
}
```

同为中文的两个模板也必须有两个 baselineId。重命名不改变 ID；结构升级产生新 revision，旧草稿仍绑定原模板版本，不能静默重载新模板破坏编辑内容。

注册来源推荐本地 SQLite 模板目录，首次以现有两份模板建立注册项。API 返回统一列表，前端下拉、预设管理、导出均消费该目录。新增模板通过注册资产和元数据完成；结构无法编辑时给出兼容检查结果，不承诺任意 DOCX 都能自动适配。

### 4.2 工作项目 DocumentWorkspace

工作项目表示同一产品/源记录的一次文档工作集合，使用独立 workspaceId，关联 sourceRecordId（如有），不能只用产品型号字符串作唯一键。

同一个型号可能有不同批次、不同源文件或不同修订；不同 workspace 之间不共享草稿。换产品必须切 workspace，防止上一份产品的英文稿被下一份产品的中文稿组合导出。

### 4.3 每基准一个独立 BaselineDraft

唯一约束：(workspaceId, baselineId)。建议保存：

- draftId、workspaceId、baselineId；
- templateRevision、draftRevision；
- 当前完整 DOCX 快照；
- 内容状态、保存状态、完成确认所在 revision；
- 当前章节、查询、预览位置、命名设置、特殊编辑权限等 UI 元数据；
- 与该草稿关联的批注/审计证据及其 revision。

不要继续由单个全局 dirty 表示全部状态。至少区分：

| 状态维度 | 值示例 | 作用 |
|---|---|---|
| 内容阶段 | 未开始、编辑中、已完成 | 是否允许导出 |
| 保存阶段 | 待保存、保存中、已保存、保存失败 | 能否安全切换/生成快照 |
| 审阅阶段 | 待审阅、通过、存在阻断项 | 复用已有审阅规则，按本稿生效 |

“加载过模板”“有一个值”“刚导出过”均不等于完成。推荐加入“完成此基准”动作：保存最新版本并检查已有审计条件后，记录 completedRevision。后续编辑提升 draftRevision，原完成标记失效，需要重新确认。这样无需为英文单独增加一套状态。

### 4.4 预设 PresetProfile

新增并强制 baselineId；保留 presetId、name、revision、字段差异、页眉页脚差异和命名规则。

- 每个预设只属于一个基准；语言相同也不能跨基准自动应用。
- UI 名称不决定归属。预设可以叫“客户A”，归属由 baselineId 决定。
- baselineId 指所属结构，不是“想输出成哪种语言”。
- 删除/归档模板时不能级联删除草稿和预设。
- 复制到同一基准可以直接复制差异；跨基准复制必须明确选择目标、校验字段映射并人工确认，不自动翻译。
- 覆盖值应支持继承、指定值、明确清空；未知字段报告未应用，不能静默成功。
- 模板升级后，预设需要兼容性检查；不靠名称包含 CN/EN 来判断兼容。

## 5. 保存与模板切换设计

### 5.1 持久化推荐

复用现有本地 SQLite 和 API，作为模板目录、预设、工作项目及草稿的正式保存位置。浏览器 IndexedDB 可作为未获服务器确认的修改恢复日志，不能成为另一套长期预设库。

草稿快照建议使用 SQLite BLOB，元数据和快照在事务内提交，避免文件落盘与数据库引用不同步。大规模快照的保留与清理后续按容量实施，但首版不得自动清除用户唯一副本。

两层分工：

- SQLite：已确认保存的版本与归属，使用 revision 做冲突检查。
- IndexedDB：崩溃恢复/断网待同步日志。恢复后展示差异，不静默覆盖服务器的新版本。
- localStorage：仅保留轻量偏好；旧预设待迁移，不能清空后直接丢弃。

这不自动打通本地 5173 与独立 Docker 的数据库。它们如需共享数据，应另行明确共享同一后端或迁移流程，本轮仅设计当前安装目录。

### 5.2 正常切换流程

```text
Edit current draft
  -> flush active input / IME composition
  -> capture current revision
  -> serialize current DOCX + UI state
  -> persist current draft
  -> load target baseline's saved draft, or create new unstarted draft
  -> restore target UI state and its own presets/review context
```

保存失败则留在原稿并显示失败原因；可提供恢复副本，但不能假装切换保存成功。慢速保存时如产生新输入，只能确认被保存的 revision，后续更改仍待保存。

连续快速切换必须有请求序号/取消过时加载的机制，防止 A→B→C 时最后返回的 B 请求覆盖 C。保存完成前切换不可错误地丢弃原稿。

### 5.3 预设编辑期间切换

基础稿和预设差异不能共用同一个可变引擎引用。每个基准保存基础稿；预设画布是该基准的派生编辑视图，保存回预设差异。

切换前分别提交当前预设差异与基础稿，不允许把“预设画布中的大量留空继承”当成基础稿保存。保存失败时不离开。返回该基准后可恢复之前的预设编辑位置，但导出仍只读已保存的基础快照和预设 revision。

### 5.4 所有进入编辑器的入口必须改造

loadEditorTemplate、importFile(editor)、commit-to-editor、仓库记录载入、重置、页眉页脚编辑、行操作、预设进入/退出都要经过同一草稿控制层。

智能匹配引擎与编辑引擎需要从当前序列化快照克隆，避免它们共享同一对象导致回看匹配结果时内容被编辑器改写。

## 6. 预设管理方案

### 创建

先选择所属模板基准，默认当前基准；再输入预设名称。列表名称来自注册数据，例如“冠志中文正式模板”“客户专用模板”，不出现额外写死的“中文预设 / 英文预设”模式开关。

### 归类

按模板基准分组，每组显示名称、预设数、兼容状态。组内提供新建、编辑、复制、删除；跨组转移不是普通拖动，必须进行兼容检查。

### 校验

前端过滤不能代替服务端校验。所有应用/导出 API 都验证：

```text
preset.baselineId == draft.baselineId
draft.templateRevision is compatible with preset schema
```

不满足则返回明确错误；不允许 fallback 到第一个预设、默认中文、默认公司或任意当前主稿。

### 前后端统一

API 统一返回 data 列表和 camelCase；客户端直接消费，不再自行拼接 targetTemplate。SQLite 是正式预设库，浏览器现有数据经迁移后按 ID/revision 合并，不能一端默认覆盖另一端自定义内容。

## 7. 导出新模型

### 7.1 从独立草稿生成计划

删除语言 × 公司笛卡尔积路由，改为明确的目标清单：

```ts
interface ExportTarget {
  targetId: string;
  workspaceId: string;
  baselineId: string;
  templateRevision: string;
  draftId: string;
  draftRevision: number;
  presetId: string | null;     // null 表示基础稿
  presetRevision: number | null;
}
interface ExportPlan {
  targets: ExportTarget[];
  formats: Array<'docx' | 'pdf'>;
}
```

用户看到的文件名只是展示与交付名称，不用作引擎缓存键或目标身份。每个目标读取其自身 draftId/revision；不存在该稿或完成标记过期时阻止该目标。

### 7.2 生成流水线

1. 提交待保存内容，读取同一 workspace 下用户选中的已完成快照。
2. 校验基准归属、模板版本、预设兼容性、批注与审计状态、格式能力、文件名冲突。
3. 冻结草稿和预设 revision；生成期间的继续编辑不影响已冻结任务。
4. 每个目标从完整已编辑 DOCX 快照克隆，基础稿不受污染；只叠加它自身基准下的预设。
5. 一个目标只生成一次 DOCX；PDF 从该份确切 DOCX 转换。只选 PDF 时，DOCX 为中间件，不加入交付包。
6. 收集各目标/格式结果并与计划核对；缺文件、失败或同名冲突不可报“全部成功”。
7. 批量入口推荐统一单个 ZIP 下载，延续用户此前“只给 ZIP”的要求；不再同时弹出多个 Word/PDF。若其他单文件按钮保留直出，应与批量入口区分。

基础稿是否导出由本次清单勾选决定，不强制带出；用户可以只选该基准的两个预设。未选择的未完成基准不阻断已经完成的基准。

### 7.3 英文尚未编辑时

模板目录中仍显示英文基准，但其导出组为“未完成，前往编辑”；复选框禁用，不生成该基准的任何预设文件。

“只有中文完成”时导出中文对应稿件即可。不能加载英文空模板、把中文值填过去或只改文件名后称为英文文件。以后如提供跨基准复制/翻译，只能作为显式起草动作，目标仍处于编辑中，不能直接获得完成资格。

### 7.4 PDF 能力与失败

新增/复用能力接口返回运行环境真实可用性，不让 UI 根据运行平台猜测。探测 Windows 安装路径与 PATH 命令，实施时分别验证实际环境；不在本轮承诺 Docker 已具备转换器。

PDF 转换使用每次任务独立的 LibreOffice 用户 profile 与临时目录，并限制并发，避免多个工作项目抢占同一进程。内部临时文件名用 targetId，避免两个不同模板同名时互相覆盖。

推荐默认完整交付：某个 PDF 失败时，明确显示失败项，保留已成功结果供重试，不自动交一个缺 PDF 的包并报全部成功。若允许下载部分成果，必须标记缺项并由用户明确选择。

### 7.5 文件名与目录

默认可按基准目录分组，例如“模板显示名_短ID/版本名.docx”，名称来自注册数据。重名必须提前检测或使用明确稳定后缀；不能用 Map(fileName) 或 ZIP 相同路径静默覆盖。

字数、非法字符、大小写冲突、重名预设均要覆盖。文件数量 = 选择目标数 × 格式数，只在计划全部成功且没有去重覆盖时成立。

## 8. UI 设计方案

沿用已确认的简洁浅色风格，使用模板基准数据驱动，不新增固定 CN/EN 或冠志/国彩的选择矩阵。

### 编辑器

- 一个“模板基准”下拉/切换列表，显示注册名称和该稿状态。
- 当前上下文展示：“模板名 / 保存中、已保存、保存失败 / 编辑中或已完成”。
- 提供“完成此基准”，并说明后续更改需要重新确认。
- 切换自动保存、恢复章节与预览位置，不再提示正常切换就会丢修改。
- 当前模板下的预设列表只显示与它绑定的项。

### 预设管理

按模板注册项分组展示；每组提供“新建预设”。用户改模板显示名后，分组立即沿用新名，预设关联不变。

### 批量导出

```text

Baseline name A                  Ready
  [ ] Base draft
  [x] Preset A1
  [x] Preset A2

Baseline name B                  Not ready -> Edit
  [disabled] Base draft / presets

Baseline name C                  Ready
  [x] Preset C1
```

界面实际显示中文业务名称；这里仅用 ASCII 结构说明层级。基准名可以包含“中文/英文”，但来自数据，不是界面编写两套固定列。

选择状态只属于本次导出草稿；取消不改长期默认选择。预览、生成、ZIP 装包消费同一 ExportPlan，避免数量和结果不一致。

## 9. 数据迁移与兼容性

### 9.1 现有内置预设

对已知旧内置 ID 制定一次性迁移映射：

- preset_guocai_cn、preset_guanzhi_cn → 现有中文正式基准的稳定 ID；
- preset_guocai_en、preset_guanzhi_en → 现有英文正式基准的稳定 ID。

这些特殊 ID 只允许出现在迁移表/初始种子中，不进入新导出调度逻辑。历史“国彩模板名”在没有独立模板资产时代表同基准的主体覆盖，不能错误注册成一份已编辑的国彩基础稿。

### 9.2 自定义旧预设

精确的 targetTemplate 别名能够唯一定位基准时自动归属；只有 language 或名称含 CN/EN 而不能唯一定位时进入“待归属”，保留原始值并让用户选择。未来同语言多个基准时尤其不能凭语言猜测。

同 ID 的服务器和浏览器数据有冲突时保存原始记录与冲突副本，不按“系统默认优先”覆盖。迁移幂等，可重试，并保留映射结果。

### 9.3 旧草稿恢复

当前没有已持久化的每基准草稿，不能在升级时凭空恢复曾经被覆盖的内容。应在仍打开的页面中尽可能捕获当前主稿、normalEngine 和预设差异；没有捕获到的其他基准显示未开始，而不是预先完成。

实施和部署前先导出未保存工作快照、SQLite 一致性备份及浏览器旧预设，再进行 schema 升级。不得用历史旧目录快照覆盖当前安装中的其他修改。

### 9.4 新模板与模板升级

新增基准只需注册新的资产、ID、元数据和可编辑结构能力；UI、预设分组、保存和导出自动消费注册信息。

模板结构升级保留旧 revision。旧稿可继续关联旧版本；迁移到新结构需差异/映射检查，未匹配字段必须可见。改显示名不触发迁移，删模板仅归档且不删除已有草稿。

## 10. 建议接口与模块拆分

以下均是拟开发内容，不是当前已经存在的 API。

| 模块/接口 | 职责 |
|---|---|
| template-registry | 统一模板 ID、名称、资产、版本、能力；前后端共享解析 |
| draft-workspace | 切换、自动保存、revision、完成确认、按源记录隔离 |
| preset-service | 基准归属、兼容性、CRUD、旧数据迁移 |
| export-plan | 计划校验、计数、命名、冻结版本，浏览器/API 共用规则 |
| export-executor | 已保存快照克隆、覆盖、逐目标审计、DOCX/PDF、ZIP |
| GET /api/msds/baselines | 列举注册基准，不依语言硬编码 |
| PUT /api/msds/workspaces/:id/drafts/:baselineId | 保存完整快照，携带 expectedRevision；冲突不覆盖 |
| GET 同草稿路径 | 读取草稿快照、版本、状态 |
| POST 同草稿路径 /complete | 标记当前 revision 完成，服务器检查条件 |
| GET /api/msds/presets?baselineId=... | 返回同基准预设 |
| POST /api/msds/export-plan | 返回目标清单、格式能力、阻断项和命名冲突 |
| POST /api/msds/export-job | 按冻结计划生成结果 |

新增模板目录、workspace、draft snapshots 表和 presets.baseline_id，均在现有 SQLite 中迁移。保留旧调用的兼容适配期，但旧 API 若缺乏归属证据不能猜默认基准；用明确错误和迁移提示处理，不能留下可绕过新约束的入口。

## 11. 开发顺序与文件影响

1. **先制止错误导出。** 移除未准备基准的语言组合选择及 fallback，统一前端/API 导出验证。
2. **建立模板注册与归属。** 现有模板种子注册、预设外键、响应格式对齐、迁移工具。
3. **建立多基准草稿。** 完整快照、保存状态、切换恢复、崩溃恢复、revision 冲突。
4. **收敛所有编辑入口。** 智能匹配投入、导入、重置、行操作、预设视图全部接入草稿控制层。
5. **接入完成状态与分组 UI。** 预设管理按基准归类；批量导出按实际已完成稿列出。
6. **实现共享导出计划。** 独立稿件克隆、预设校验、命名、ZIP，移除旧硬编码公司/语言分支。
7. **完善 PDF。** 能力探测、转换隔离、失败可见与数量核对。
8. **端到端验收。** 至少三个基准，其中两个同语言，证明扩展依赖 ID 而不是语言分支。

主要影响 main.js、docx-engine.js、msds-db.js、msds-api-controller.js、pdf-converter.js、styles.css 与有针对性的测试。server.mjs/vite.config.js 应继续使用同一 API 路由，不另开正式服务或端口。Python 桌面模块不是当前 Web 需求的实现目标。

## 12. 验收案例

| 案例 | 必须达到的结果 |
|---|---|
| 只编辑并完成基准 A | 只能导出 A 基础稿和 A 的预设；B 的预设不可选 |
| A→B→A | A 的字段、页眉页脚、增删行、图片和 UI 位置恢复 |
| A/B 保存后刷新、重启 | 均恢复各自稿件，状态与 revision 一致 |
| 同语言 A 和 C | 各自独立，A 预设不能应用到 C |
| 新增第三模板 | 不改导出分支也能出现、编辑、保存、创建预设和导出 |
| 中文标记与英文标记 | 重新打开导出 DOCX，只有对应基准标记，不发生原样跨语言复制 |
| 预设切换时待保存 | 差异不丢失，不把空白预设画布保存成基础稿 |
| 修改已完成稿 | 完成确认失效；重新确认前该 revision 不可导出 |
| 不同源产品/批次 | 草稿不能串用；任务必须属于同一 workspace |
| 保存失败/磁盘满/断网 | 显示失败并保留当前内容，不能宣称安全切换成功 |
| 两个标签页并发 | 旧 revision 不静默覆盖新稿，显示冲突 |
| 新模板加载失败 | 保留原稿和选择，不回退到别的模板生成输出 |
| 仅 Word | ZIP 里只有 DOCX |
| 仅 PDF | DOCX 只作中间结果，ZIP 里只有 PDF |
| Word+PDF | 两种文件均由同一个冻结 DOCX 目标生成 |
| PDF 失败 | 明确失败，不缺项仍报全部成功 |
| 同名输出 | 预检阻断或明确改名，不用 filename Map 静默合并 |
| 请求中篡改 presetId | 服务端仍拒绝跨基准预设 |
| 旧预设迁移两次 | 不重复、不丢失；歧义项保留待归属 |
| 导出后反向解析 | 字段、页眉页脚、表格结构与对应基础稿/预设符合预期 |

自动化测试必须覆盖内容身份和来源关系；不能只断言有文件、文件够大或扩展名正确。

## 13. 方案中提出的默认取舍

以下是建议实现规则，供评审，不代表已上线：

- 持久保存优先复用本地 SQLite；浏览器恢复日志不替代正式保存。
- “已完成”由明确动作确认并绑定草稿 revision，普通编辑不会自动宣称完成。
- 格式选择默认作用于本次已选所有版本；首版不增加逐版本格式开关。
- 批量入口统一 ZIP，基础稿可取消勾选，允许只交预设。
- 转换缺项默认不报完整成功；部分成果下载如提供，必须显式标注。
- 跨基准内容复制、自动翻译和结构迁移不作为首版自动行为。

这些取舍都在当前用户目标内给出了可实施方向，没有把正常开发步骤包装成额外审批。
