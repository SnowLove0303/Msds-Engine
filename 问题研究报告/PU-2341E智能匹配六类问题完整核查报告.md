## 三、问题一：标签和值错位

### 1. Section 3 组分汇总写入 CAS 表头列

原始模板 Section 3 的表头结构是：

```text
化学品名称 | CAS编号 | 含量%（w/w）
```

匹配后变成：

```text
化学品名称 | - 聚氨酯聚合物 (CAS: 商业机密, 含量: 30-40)
           | - 水 (CAS: 7732-18-5, 含量: 60-70)
           | - 三乙胺 (CAS: 121-44-8, 含量: 0.5-2)
           | 含量%（w/w）
```

这里的结构错误可以直接由模板和结果表格确认：

- 原本承担 `CAS编号` 的第二列表头被覆盖；
- 组分汇总值被写到表头行，而不是独立的说明行或值行；
- 汇总文本继承了表头的下划线样式；
- 第二列宽度约 32%，长文本被压成窄列纵向换行；
- 实际三个组分行仍然存在，但表头已经不能正确表达三列含义。

这不是对组分是否需要汇总的业务判断，而是汇总内容占用了 `CAS编号` 表头单元格。

### 2. Section 8 值进入标签列

原始模板 Section 8 对应结构为：

```text

右侧合并值格：建议戴上防护手套。
```

```text
左侧合并标签格：喷涂过程中要求有呼吸防护设备。

```

同时上一行已经存在：

```text

```

因此同一段文本同时出现在上一行的值列和下一行的标签列，且下一行值格为空。原模板的 `手部防护：` 标签也不再出现。

### 3. Section 11 同级毒理子项被压到错误层级

## 十一、最终判断

当前智能匹配结果不能作为“只使用源文件事实、严格套入模板标签结构”的合格结果。主要阻断点不是匹配数量不足，而是写入目标和模板结构没有保持一致：

```text
源识别值
   -> 目标标签/值槽位定位不稳定
   -> 部分值进入标签列或错误同级项
   -> 部分源值缺失
   -> 换行和表头结构改变
   -> 模板加粗层级被破坏
   -> 无值标签仍然可见
```

本次最应优先修复的顺序是：

1. 先修复多列合并行和值列定位，解决 Section 8 的标签列污染；
2. 修复 Section 3 组分汇总不得写入表头列；
3. 保护 Section 11 同级加粗子标签和值格边界；
4. 建立源值逐项存在性检查，拦截 Section 5.1、8“建议”、9 相对密度和 15 法规值丢失；
5. 恢复有意义的源换行，清除不应出现的额外空行；
6. 在 Section 2、8、10 中执行无值完整项隐藏，并用“剪枝字段数 = 实际隐藏/删除项数”做最终审计；
7. 对加粗运行区做模板前后差异审计，除 Section 9 受控编号重排外，不允许加粗标签内容变化。

#### 七、模板结构角色与 UI 字体格式深度审计

本节专门核查“本来应该是标签，却没有按标签角色呈现”的问题，以及匹配表和编辑表是否使用了相同的标签/值结构和文本格式。

##### 1. Section 3：CAS 和含量表头没有使用统一的标签字体角色

当前匹配页面的 Section 3 表头视觉结构是：

```text
化学品名称 | CAS编号 | 含量%（w/w）
```

但 DOM 样式实际表现为：

```text
化学品名称：font-weight:700; text-decoration:underline
CAS编号：font-weight:400; text-decoration:underline
含量%（w/w）：font-weight:400; text-decoration:underline
```

这三个单元格都承担表头/标签职责，但当前 UI 只把第一列按标签或表头角色渲染，第二列和第三列沿用了普通值文本角色。结果是：

- `化学品名称`视觉上是加粗标签；
- `CAS编号`和`含量%（w/w）`是普通体；
- 三个列标题的字体层级不一致；
- 匹配工作区和编辑器如果使用不同的角色判断，会出现同一个模板表头在两个工作区样式不一致。

这个问题不能只靠把文字加粗解决。底层模板 Profile 应将 Section 3 的三列全部标记为：

```text
role = table-header
fontRole = label-header
bold = true
underline = template-defined
editable = false
```

`CAS编号`和`含量%（w/w）`不能因为它们位于第 2、3 列就被 `cellRole()` 当成普通值。表头角色优先级应该高于列位置和普通加粗/非加粗判断。

##### 2. Section 3：`3.1 产品类型`在标签结构下仍然是空值

当前 GUI 中：

```text
源识别表：3.1 产品类型： | 混合物
标准匹配表：3.1 产品类型： | 空白单元格
```

标签角色本身显示正确，但值没有进入同一模板值格。这说明当前问题不是字体，而是：

```text
源标签确认成功
源值确认成功
目标标签定位成功
目标值格写入失败或读取失败
```

这个案例必须作为模板适配和写入计划的回归样例，验证“标签、值、目标值格”三者是否真正绑定在同一模板行。

##### 3. Section 8：模板标签残留文本仍混在加粗标签中

当前 GUI 的 Section 8 手部防护行显示为：

```text
左侧标签：手部防护：  喷涂过程中要求有呼吸防护设备。
右侧值：防护手套合适材料：EN 374
       - 氟化橡胶-FKM……
       - 丁基橡胶-IIR……
       - 丁腈橡胶-NBR……
```

模板 Profile 中，左侧合并格应拆成：

```text
加粗标签：手部防护：
值或残留文本：需要单独判定
```

当前结果把“喷涂过程中要求有呼吸防护设备”继续显示在标签区域，并且它与手部防护标签处于同一个左侧格。这样会导致：

- 呼吸防护值重复出现在手部防护标签区域；
- 手部防护标签和呼吸防护值无法区分；
- 匹配工作区和编辑器会继承同一个混合角色；
- 后续写入手部防护值时可能继续污染标签格。

这里需要把模板原有残留文本标记为独立的模板缺陷或残留值节点，不能把它和加粗标签一起当作一个标签字符串。

但值只进入了第一行的经口区域，吸入和经皮两个同级值格为空。这里的问题不是简单字体错误，而是“同级标签和值关系没有完成”。模板结构已经把三个子项分开，匹配结果不能把一个大段值只挂到第一个子项，同时留下另外两个空值格。

每个事实都要绑定到对应的子标签和值格，不能把它们合成一个 `s11:reproductive_toxicity` 后只写第一行。

##### 6. Section 13：普通值文本被 UI 渲染成标签角色

当前标准匹配表中，下面两段源说明显示在左侧单列区域：

```text

```

它们被渲染成 `label-parent-row`，但从源结构看，这两行没有标签和值分隔，它们是无标签说明值。

正确角色应该是：

```text
role = note/value-only
fontRole = value
label = null
value = 完整原文
```

不能因为单元格位于第一列，就自动把它渲染成标签。第一列只表示几何位置，不代表语义角色。

##### 7. Section 15：法规文本被显示为普通标签行

当前 GUI 的 Section 15 中，以下内容以单列 `label-parent-row` 形式显示：

```text
物质或混合物的相关安全、健康和环保法律法规
危险化学品安全管理条例，国务院令344号
GB/T 16483-2008 化学品安全技术说明书内容和项目顺序
GB 13690-2009 化学品分类和危险性公示通则
GB 20576-GB20598 化学品分类，警示标签和警示性说明安全规范
```

这些文本使用的是普通体，但 DOM 结构仍被包装成 `label-parent-row`，没有独立值节点。结果是用户看不到标签和值的关系，也无法在编辑器中按照值格进行安全写入。

Section 15 的 Profile 必须支持单列值行：

```text
role = value-only / source-note
label = null
value = full text
editable = according to Profile
```

法规文本不能被当作普通标签，也不能因为没有第二列就被丢弃。

##### 8. Section 16：单列免责声明没有生成值角色

源识别表中有完整免责声明，但标准匹配表只有：

```text
16. 其他信息
```

没有值行，也没有单列值节点。这里需要将 Section 16 的单列行明确标记为：

```text
role = value-only
valueCell = same XML cell
paragraphPolicy = preserve source paragraphs
```

不能用“只有一列”推断它是结构标题或空行。

#### 八、标签和值字体规则必须独立于列位置

当前 UI 存在一个底层设计问题：部分角色判断同时依赖“是否加粗”和“处于哪一列”。这会造成：

```text
第一列普通文本 -> 被误认为标签
第二列普通文本 -> 被当作值
第一列加粗文本 -> 被当作标签
第二列加粗文本 -> 可能被当作值或子标签
```

正确的角色优先级应为：

```text
模板 Profile 明确角色
    > 表头/结构行角色
    > Section 专属角色
    > 同段冒号关系
    > 同行合并关系
    > 网格列位置
    > 加粗/非加粗证据
    > 字符长度和别名匹配
```

加粗只是角色证据之一，不能因为文字处于第一列就强制成为标签，也不能因为文字处于第二列就强制成为值。

#### 九、匹配工作区和编辑器必须共用同一套角色模型

当前需要避免以下情况：

```text
识别表用一套标签/值判断；
匹配表用另一套标签/值判断；
编辑器又按第三套规则判断可编辑区域。
```

三个界面必须共享同一套模板 Profile 和角色模型：

```json
{
  "cellId": "tc-8-3-left",
  "role": "label",
  "fontRole": "label",
  "bold": true,
  "editable": false,
  "mergeGroupId": "merge-8-3-left"
}
```

```json
{
  "cellId": "tc-8-3-right",
  "role": "value",
  "fontRole": "value",
  "bold": false,
  "editable": true,
  "mergeGroupId": "merge-8-3-right"
}
```

结构化识别表、智能匹配表、模板编辑器和导出写入必须使用同一个 `cellRole` 和 `templateSlot` 结果，不能各自重新推断。

#### 十、Section 3 表头需要专用 Header Role

Section 3 当前暴露的字体问题说明普通标签/值规则不足。

应为 Section 3 表头建立专用角色：

```json
{
  "section": 3,
  "row": 3,
  "cells": [
    {"role": "table-header", "key": "component-name"},
    {"role": "table-header", "key": "cas"},
    {"role": "table-header", "key": "concentration"}
  ]
}
```

这三个表头都应该使用统一的 `label-header` 字体策略。不能让 `CAS编号` 和 `含量%（w/w）`因为位于值列就沿用普通值字体。

匹配表和编辑器都必须统一：

```text
表头字体：同一 header role
表头加粗：由 Profile 决定
表头下划线：由模板基线决定
表头不可编辑
表头不参与值写入
```

#### 十一、当前 GUI 复核后的最终结构问题

本次用户界面复核确认以下问题仍然存在：

1. Section 3.1 `混合物`源值没有显示在标准匹配值格；
2. Section 3 的 CAS 和含量表头虽然已经占据正确列，但字体角色仍需统一为表头/标签角色；
3. Section 8.1 控制参数源说明没有进入标准值格；
4. Section 8 手部防护标签仍含有呼吸防护残留文本；
5. Section 8 OEL 空结构仍显示；
6. Section 9 其他信息仍显示为 `9.23`，连续编号策略没有明确落地；
7. Section 11 急性毒性三个同级子项的值关系没有完成；
8. Section 11.7 的三个加粗子标签存在，但对应值格为空；
9. Section 13 无标签源说明被归类到左侧标签区域；
10. Section 13 处理方法的源换行被压成一行；
11. Section 15 法规文本被包装成普通标签结构，没有独立值角色；
12. Section 16 免责声明没有进入标准匹配表；
13. 匹配表、编辑器和模板原始结构还没有完全共用同一个角色模型。

#### 十二、最终实施要求

后续实现不能只继续增加别名或关键词。必须先完成以下底层调整：

1. 为模板每个单元格建立固定的 `role`、`fontRole`、`mergeGroupId` 和 `slotId`；
2. 识别和匹配过程只产生候选标签、候选值及关系证据；
3. Section 3 表头使用独立的 `table-header` 角色；
4. 第一列普通文本不能自动视为标签；
5. 单列值行必须支持 `value-only/source-note` 角色；
6. Section 11 子标签和值必须逐项建立关系；
7. 写入只允许进入 Profile 指定的真实值格；
8. 匹配页和编辑器必须复用同一份结构模型；
9. 匹配完成后检查标签字体、值字体、加粗、下划线、对齐、换行、合并和空值隐藏；
10. 任何角色不确定、值格不确定、合并关系不确定的行都必须阻断写入并进入复核。

本次 GUI 复核证明，下一阶段的核心不是继续扩大匹配召回率，而是让模板结构角色、标签/值关系和 UI 呈现完全统一。只有这样，未来模板版本变化时，识别模块、匹配模块和编辑模块才能使用同一份结构 Profile，避免出现“识别看起来正确、匹配位置错误、编辑器又按另一套结构显示”的问题。


## 早期模板内容残留根因分析


**项目：** MSDS Studio  
**日期：** 2026-10-05  
**范围：** 浏览器端“DOCX 识别 → 智能匹配 → 模板编辑”链路  
**结论类型：** 代码与 OpenSpec 约束对照分析；未对某一份具体用户源 MSDS 做逐字段复现。

#### 结论

问题的主要根因已经定位：智能匹配在标准模板副本上执行“命中字段写入”，但普通章节的空项、未匹配项和冲突项不会清空目标格里原有的模板内容；同时，界面允许用户不经审核直接导入编辑器。只要源文件中某个字段没有映射成功，模板里的示例值、占位文字或默认文字就可能继续留在最终工作副本中，被误认为是该源产品的事实。

此外，Section 15 存在固定法规清单自动填入逻辑；Section 3 和 Section 14 也有自动补值/级联规则。这些规则会生成或改写源文字，必须受来源证据和审核门槛约束。因此，“模板内容残留”和“源事实映射不完整”是同时存在的风险。

#### 对照的项目约束

项目全局规范明确规定：模板提供格式，源文件提供产品事实；不得把模板示例和源文件事实合并。规范要求发布前清除模板示例；源文件未提供的字段应按批准规则抑制，不能将模板原值当作事实输出。[全局约束 G-01、G-14～G-17](../MSDS覆写全局约束体系与八格式规范报告.md#二-msds-全局约束核心体系八大通用维度)

智能匹配 OpenSpec 要求未知标签和冲突事实形成待复核项；全局匹配规格要求将相互冲突的源事实标记为 `REVIEW_AMBIGUOUS`，不可静默覆盖。[智能匹配引擎规格](../openspec/changes/smart-matching-workbench/specs/smart-matching-engine/spec.md) [全局匹配规格](../openspec/changes/global-matching-engine-constraints/specs/global-matching-engine/spec.md#requirement-canonical-slot-binding-without-positional-inference)

#### 修复方向

1. 每次匹配从新模板克隆后，先按安全编辑白名单清理由源文件负责的值格；保留标签、章节骨架和格式，再写入有明确来源依据的值。
2. 为每个源事实保留 Section、行/单元格定位、原文、目标槽位、匹配方式和转换记录；匹配结果页显示来源证据与项目状态。
3. `UNMATCHED`、`REVIEW_AMBIGUOUS` 及无法安全表示的内容应阻断导入/导出。完成复核并选定经批准的合并、忽略或来源保留处置后，才解除阻断。
4. 按全局与章节规则处理缺项：该删除的完整条目整体抑制；允许标准缺失话术的字段采用明确话术；不得把模板示例当作源值保留。
5. 移除 Section 15 无来源法规清单；Section 3/14 的默认补值和级联仅可使用明确来源事实及批准规则，否则转入人工复核。
6. 增加端到端回归场景：目标模板原有非空值但源字段缺失、同槽位冲突、未知标签、Section 9 剪枝、实质否定结论保留、模板示例清零，以及导出重开后逐项核验来源值并确认未决项会阻断。

## 十九、全 16 Section 标签对齐、垂直居中、换行和字体角色审计

本节专门核查当前 Web 匹配表的用户界面和渲染代码，重点检查序号、标签首字、子级缩进、换行续行、垂直居中、标签字体和值字体，以及严重的窄列竖向折行。

### 1. 标签格实际被 CSS 强制顶端对齐

当前样式存在：

```css
.structured-table td:first-child {
  vertical-align: top !important;
}
```

在当前浏览器对 16 个 Section 的实际 DOM 测量中，结构化表内标签单元格的 computed `vertical-align` 均为 `top`。这直接违反全部标签格垂直居中的要求，并会导致：

- 多行值旁边的标签始终贴在顶部；
- 合并标签格不能在对应行高内垂直居中；
- Section 5、6、7、8、11、13 等高行标签的视觉基线不稳定；
- 模板原始 `w:vAlign` 即使是 center，也会被 CSS 的 `!important` 覆盖。

### 2. 序号和标签首字没有固定列

当前序号通过 `.sequence-run` 作为 inline-block 插入标签文本流。实际测量结果显示：

| 序号类型 | 标签首字起始 X 坐标 |
|---|---:|
| Section 1～9 的 `N.1` | 约 888 |
| Section 10～12 的 `N.1` | 约 898 |
| Section 11.10 | 约 907 |

序号越长，标签首字越向右移动。当前不是固定的“序号槽 + 标签槽”布局，所以无法满足 16 个 Section 标签首字共用一条垂直线。

正确结构应当是：

```text
| 固定宽度序号槽 | 标签文本槽                       |
| 1.1            | 产品名称：                       |
| 10.1           | 化学稳定性：                     |
| 11.10          | 附加信息：                       |
```

### 3. 多行标签续行没有悬挂缩进

Section 11.8 的实际浏览器测量结果：

```text
首行序号：x ≈ 837
首行标签文字：x ≈ 898
第二行标签文字：x ≈ 837
第三行标签文字：x ≈ 837
```

当前续行回到了单元格左边，而没有和首行标签文字对齐。原因是序号和标签仍在同一个普通 inline 流中，没有独立的标签文字槽位，也没有 hanging indent。

### 4. 子级标签缩进没有统一的模板角色基础

当前 CSS 使用固定：

```css
.label-child-row {
  padding-left: 2.2rem !important;
}
```

一级子标签在多个 Section 中大约从 x=872 开始，但 Section 11 的二级子标签位于独立子列，首字大约从 x=1036 开始。当前系统同时混用了：

```text
序号 inline 流
固定 padding-left
独立子标签列
```

需要由模板 Profile 明确保存：

```text
parentLabelSlot
childLabelSlot
sequenceWidth
childIndentWidth
childValueStart
mergeGroupId
```

不能靠全局 `padding-left` 解决所有表格。

### 5. Section 8、Section 11 标签列存在严重窄列折行

Section 8 的以下标签列宽约 160px：

```text
防护手套的合适材料：
氟化橡胶 –FKM:
丁基橡胶 –IIR：
丁腈橡胶 – NBR：
```

Section 11 的 `吸入：`、`经皮：`、`致畸形`、`体外遗传毒性`位于更窄的子标签列。当前 UI 中部分文字接近逐字竖向换行。

CSS 没有直接设置 `writing-mode`，但窄列、固定缩进、`word-break: break-word` 和 `overflow-wrap: anywhere` 的组合产生了严重的竖向视觉效果。这不符合标签必须保持水平可读的要求。

### 6. 第一列普通值可能被错误使用标签字体

`renderParagraph()` 当前对第一列使用标签角色样式：

```javascript
const roleStyle = (isFirstColumn && !isSec15)
  ? effectiveRoleStyles.label
  : ...
```

这意味着第一列中的普通值、无标签说明和单列值，可能被套用标签字体。第一列只是几何位置，不等于标签语义。Section 13、Section 16 的单列值必须使用独立的 `value-only` 或 `source-note` 角色。

### 7. Section 3 的 CAS 和含量表头没有统一标签字体

当前 GUI 的 Section 3 表头实际样式为：

```text
化学品名称：font-weight:700; text-decoration:underline
CAS编号：font-weight:400; text-decoration:underline
含量%（w/w）：font-weight:400; text-decoration:underline
```

三个单元格都承担表头/标签职责，但只有第一列使用了表头/标签字体，第二、三列仍按普通值字体渲染。

Section 3 表头必须定义为独立角色：

```text
role = table-header
fontRole = label-header
bold = true
editable = false
```

不能因为 CAS 和含量位于非第一列，就把它们交给普通值字体规则。

### 8. Section 13、Section 15 的单列值没有独立值角色

Section 13 的无标签废弃说明在 UI 中被包装为 `label-parent-row`，但它们实际上是值/说明文本。Section 15 的法规文本也以 `label-parent-row` 显示，即使其字体是普通体，结构角色仍然是标签行。

正确角色应当是：

```text
role = value-only / source-note
label = null
value = 完整源文本
fontRole = value
```

### 9. Section 16 单列免责声明没有生成值角色

源识别区有完整免责声明，但标准匹配表只有 Section 16 标题，没有值行。单列免责声明必须被识别为单列值，不应该因为没有第二列而消失。

## 二十、实现目标

### 1. 序号和标签使用双槽位

建议渲染结构：

```html
<div class="label-line label-parent">
  <span class="sequence-slot">11.8</span>
  <span class="label-text-slot">特异性靶器官系统毒性（一次接触/反复接触）：</span>
</div>
```

```css
.label-line {
  display: grid;
  grid-template-columns: var(--sequence-width) minmax(0, 1fr);
  align-items: center;
}

.sequence-slot {
  width: var(--sequence-width);
  white-space: pre;
}

.label-text-slot {
  min-width: 0;
  word-break: normal;
  overflow-wrap: anywhere;
}
```

续行必须在 `label-text-slot` 内换行，不能回到整个标签单元格左边。

### 2. 标签格使用 Profile 控制垂直对齐

模板 Profile 应为标签格保存：

```text
verticalAlign = center
labelRole = parent / child / table-header
fontRole = label / label-header
sequenceWidth
childIndentWidth
```

CSS 不能再用 `.structured-table td:first-child { vertical-align: top !important; }` 覆盖所有模板设置。标题、说明和值格需要按照 Profile 分别处理。

### 3. 区分 table-header、label、value、value-only

统一角色：

```text
table-header：表头，不可编辑，使用表头字体
label-parent：父级标签，加粗
label-child：子级标签，加粗，使用稳定缩进
value：标签右侧的普通值
value-only：没有标签的单列值
source-note：源文件说明性值
title：Section 标题
```

识别、匹配、编辑和渲染必须共用这些角色，不能在三个模块中分别依赖列号重新猜测。

## 二十一、最终 GUI 审计结论

当前 Web 的 16 个 Section 已确认存在以下全局问题：

1. 标签格实际被强制为顶部对齐，没有实现垂直居中；
2. 序号长度变化会改变标签首字 X 坐标，无法保证 16 个 Section 共用一条垂直基线；
3. 长标签续行没有对齐首行标签文字；
4. Section 8 和 Section 11 的窄子标签列会产生严重竖向折行；
5. 第一列普通值可能使用标签字体；
6. Section 3 的 CAS 和含量表头没有统一的标签/表头字体角色；
7. Section 13、Section 15 单列值被包装为标签结构；
8. Section 16 单列免责声明缺少值角色；
9. 匹配表和编辑器尚未完全复用同一套模板角色和结构 Profile。

这些问题不能通过继续增加别名或关键词解决。下一阶段应先建立统一的模板角色模型、固定序号/标签双槽位、垂直居中策略、子级缩进策略和单列值角色，再继续处理 Section 具体映射。
