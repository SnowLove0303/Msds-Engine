# MSDS 模板结构变更兼容与快速接入方案报告

**项目：** MSDS Studio  
**日期：** 2026-10-06  
**范围：** CN/EN 冠志模板发生结构性变更后的模板读取、结构识别、智能匹配和安全接入  
**目标：** 新模板载入后能够精准读取结构，快速建立兼容配置，并且不破坏现有识别规则、语义映射规则和模板保护规则。

## 一、核心结论

以后 CN 或 EN 冠志模板发生结构性变更，不能直接用新 DOCX 覆盖现有模板文件，也不能让智能匹配继续沿用旧模板的行号、列号或合并单元格假设。

正确方案是把整个流程拆成四层：

```text
源 DOCX 识别
    |
    v
标准语义槽位
    |
    v
模板版本 Profile
    |
    v
当前模板的标签格 / 值格 / 合并结构
```

识别模块和智能匹配只负责回答“源内容属于哪个语义槽位”；模板 Profile 负责回答“这个槽位在当前模板版本的哪个真实值格”。这样模板结构变化时，可以新增模板适配 Profile，而不需要把模板坐标、业务规则和源文件匹配规则混在一起修改。

对于完全未知的模板，程序不能直接猜测并导出。程序可以先读取、分析和展示新结构，但必须先完成 Profile 建立和结构验证，才能进入正式匹配。

## 二、当前程序的结构依赖

当前程序已经具备部分可复用能力：

- [docx-engine.js](../web/src/docx-engine.js) 可以解析 DOCX 表格、行、单元格、合并关系、列宽、段落、加粗运行区和非加粗运行区；
- [smart-matching.js](../web/src/smart-matching.js) 通过 Section 插槽和中英文别名字典进行语义匹配；
- `cleanSlateTemplate()` 负责清理模板工作副本中的值；
- `applyMatchResultToEditor()` 负责把匹配结果写回模板、处理 Section 3 组分、Section 9 剪枝和 Section 8 特殊结构；
- `cellRole()`、`resolveSlotBySemantics()` 和 `collectTemplateSlots()` 已经包含标签和值角色识别基础。

当前风险在于，部分逻辑仍然把语义匹配和模板坐标绑定在一起，存在以下隐含假设：

```text
某个字段固定在某个 rowIndex
某个值固定在某个 cellIndex
最后一个单元格就是值格
某个合并行的 row.cells[1] 一定是值格
Section 3 的 CAS 永远在第 2 列
Section 8 的值永远在 row.cells[1] 或最后一格
Section 11 的同级子项永远按当前行顺序排列
```

一旦模板改变行、列、合并关系或加粗角色，这些假设就可能导致值写入标签列、表头被值覆盖、同级子标签被清除或值格被错误清空。

## 三、模板必须采用版本化管理

模板不能只依赖文件名。每个模板文件都必须登记唯一的模板身份、版本和哈希：

```json
{
  "templateId": "cn-guanzhi",
  "version": "2.0",
  "language": "zh-CN",
  "company": "guanzhi",
  "sha256": "模板文件哈希",
  "sectionCount": 16,
  "profileId": "cn-guanzhi-v2"
}
```

建议的资源组织方式：

```text
web/public/templates/
├─ CN_Guanzhi_v1.docx
├─ CN_Guanzhi_v2.docx
├─ EN_Guanzhi_v1.docx
└─ EN_Guanzhi_v2.docx
```

旧模板不能被新模板覆盖。历史任务、既有导出文件和问题复现都需要继续使用旧模板版本。

模板版本登记至少需要保存：

- 模板语言；
- 公司；
- 版本号；
- SHA-256；
- Section 数量；
- 表格数量和顺序；
- 模板 Profile 版本；
- 是否支持 Section 3 动态组分行；
- 是否支持 Section 9 剪枝和重编号；
- 页眉、页脚和产品型号锚点。

## 四、载入新模板后的结构识别流程

新模板进入程序后，不能直接进入智能匹配，应先经过结构扫描。

### 1. 读取基础结构

程序需要扫描并记录：

```text
Section 编号和标题
表格数量和顺序
每个表格的行数、列数
每个单元格的 col、row、colspan、rowspan
列宽、行高和表格边框
标签文本和值文本
加粗运行区和非加粗运行区
段落数量和换行数量
序号运行区
页眉和页脚文本位置
```

### 2. 建立结构指纹

结构指纹不能只比较表格文字，还要包括几何和角色信息：

```json
{
  "section": 8,
  "tableIndex": 7,
  "rowCount": 16,
  "columnCount": 5,
  "rows": [
    {
      "row": 3,
      "cells": [
        {"col": 0, "colspan": 2, "role": "label", "bold": true},
        {"col": 2, "colspan": 3, "role": "value", "bold": false}
      ]
    }
  ]
}
```

这样可以区分下面两种表格：

```text
标签 | 值
```

和：

```text
标签跨两列 | 值跨三列
```

文字相同并不代表可以使用相同的写入方式。合并范围改变后，`row.cells[1]` 可能仍然指向左侧标签格的别名。

### 3. 识别 Section 内部槽位

模板 Profile 应该记录每个语义槽位的标签格和值格，而不是只记录行号：

```json
{
  "slot": "s8:hand_protection",
  "label": "手部防护",
  "labelCell": {
    "row": 3,
    "col": 0,
    "colspan": 2
  },
  "valueCell": {
    "row": 3,
    "col": 2,
    "colspan": 3
  },
  "labelRole": "bold",
  "valueRole": "non-bold",
  "allowLabelEdit": false,
  "preserveLineBreaks": true
}
```

Section 3 的 Profile 应明确记录：

```json
{
  "section": 3,
  "componentTable": {
    "headerRow": 3,
    "columns": {
      "name": 0,
      "cas": 1,
      "concentration": 2
    },
    "componentRows": "dynamic"
  }
}
```

Section 9 的 Profile 应明确记录：

```json
{
  "section": 9,
  "renumber": true,
  "pruneMissingRows": true,
  "allowQualifier": true,
  "qualifierRequiresSourceEvidence": true
}
```

## 五、模板 Profile 与语义匹配规则必须分层

未来的匹配流程应分为三层。

### 1. 语义层

语义层只负责将源标签归一化为标准槽位：

```text
“防护手套” -> s8:hand_protection
“CAS编号” -> s3:cas
“pH值” -> s9:ph
“危险分解产物” -> s10:hazardous_decomposition
```

这一层使用现有的 `SECTION_SLOT_REGISTRY`、`resolveSlotBySemantics()` 和中英文别名字典。

### 2. 模板适配层

模板适配层负责将语义槽位定位到当前模板版本的真实值格：

```text
s8:hand_protection
    -> CN Guanzhi v1: row 3, col 2, colspan 3
    -> CN Guanzhi v2: row 4, col 1, colspan 4
```

匹配层不再直接决定 `rowIndex` 和 `cellIndex`。

### 3. 写入策略层

写入策略层负责判断：

- 是否允许写入；
- 是否允许清空；
- 是否允许删除整行；
- 是否必须保留换行；
- 是否允许修改标签；
- 是否需要重新编号；
- 是否必须保留合并单元格；
- 是否必须保留加粗运行区。

这样，模板结构变化不会污染源内容匹配规则。

## 六、新模板载入时的三种状态

### 1. 已登记且兼容

如果模板 SHA-256 和已登记 Profile 一致，并且结构验证通过：

```text
模板版本：CN Guanzhi v2
结构验证：通过
目标槽位：完整
可以进入智能匹配
```

### 2. 文件名相同但结构发生漂移

如果文件名相同但哈希或结构指纹变化：

```text
检测到模板结构漂移
当前文件不再符合 CN Guanzhi v1 Profile
禁止直接匹配
需要建立 CN Guanzhi v2 Profile
```

不能继续沿用旧 Profile。

### 3. 完全未知模板

未知模板可以被读取和展示，但不能直接导出：

```text
已读取模板结构
未找到兼容 Profile
请确认 Section、标签格和值格映射
```

完成接入确认并保存 Profile 后，才允许正式匹配。

## 七、快速接入新模板的方式

为了避免每次模板变化都需要大量改代码，建议增加模板接入检查页，自动展示：

```text
Section 1
  产品名称标签：已识别
  中文名称值格：已识别
  供应商信息区域：已识别

Section 3
  三列表头：已识别
  化学品名称 -> 第 1 列
  CAS编号 -> 第 2 列
  含量 -> 第 3 列

Section 8
  呼吸防护值格：已识别
  手部防护值格：已识别
  合并列关系：已验证

Section 9
  理化槽位：已识别
  剪枝能力：已识别
  连续编号：已识别

Section 11
  急性毒性子标签：已识别
  生育力子标签：已识别
  致畸形子标签：已识别
  体外遗传毒性子标签：已识别
```

能够唯一识别的部分自动生成 Profile；不能唯一识别的部分标为待确认。确认完成后保存 Profile，不需要将坐标判断散落到匹配代码中。

## 八、匹配开始前必须做结构兼容性检查

匹配入口必须先检查：

```text
Section 数量是否正确
Section 顺序是否正确
目标槽位是否存在
标签格是否仍然加粗
值格是否仍然是非加粗运行区
合并单元格是否符合 Profile
目标值格是否可写
Section 3 三列组分结构是否完整
Section 8 右侧合并值格是否存在
Section 11 子标签是否存在
页眉和页脚锚点是否存在
```

任何关键项不通过，都应停止：

```text
模板结构与当前 Profile 不兼容，不能继续匹配。
```

不能先匹配、导入和导出，再依赖人工发现值已经进入标签列。

## 九、清空模板值必须使用 Profile

当前的 `cleanSlateTemplateRecord()` 应逐步从按 Section 硬编码，改为使用 Profile：

```text
Profile 标记值格 -> 允许清空或写入
Profile 标记标签格 -> 禁止清空
Profile 标记序号格 -> 禁止清空
Profile 标记结构行 -> 按规则保留
Profile 标记可剪枝行 -> 允许整行删除
```

清空动作不应依赖：

```text
row.cells[1]
row.cells[row.cells.length - 1]
固定 Section 行号
固定列号
```

尤其是 Section 8 这类多列合并表格，必须通过底层 XML 单元格身份和 colspan 关系确认真正的值格。

## 十、模板变更后的结构审计

匹配完成后要比较：

```text
原始模板
匹配后的工作副本
模板 Profile
```

至少检查：

- 标签文本是否变化；
- 加粗运行区是否变化；
- 标签和值角色是否变化；
- 表头文字是否变化；
- `rowspan` / `colspan` 是否变化；
- 列宽和行高是否变化；
- 值格数量是否变化；
- 有源值的槽位是否都有目标值格；
- 无源值的槽位是否按规则隐藏；
- 源文件换行是否被保留；
- 不允许修改的模板文字是否发生变化。

以本次 PU-2341E 为例，以下内容应该在导出前直接阻断：

```text
Section 3 row 3 col 1
原模板：CAS编号
匹配后：组分汇总文本
结果：表头和值角色冲突

Section 8 row 3 col 0
原模板加粗标签：手部防护
匹配后加粗内容：喷涂过程中要求有呼吸防护设备
结果：加粗标签被覆盖

Section 11 row 12~14
原模板加粗子标签：生育力 / 致畸形 / 体外遗传毒性
匹配后：子标签被清除，值被合并
结果：同级结构变化
```

## 十一、模板接入的正式流程

以后新模板的标准接入流程应为：

```text
收到新模板
    |
    v
计算 SHA-256 和结构指纹
    |
    v
查找已登记 Template Profile
    |
    +-- 已登记且兼容 --> 允许匹配
    |
    +-- 未登记或结构漂移 --> 模板接入检查
                                  |
                                  v
                           生成新 Profile
                                  |
                                  v
                          使用真实样例试匹配
                                  |
                                  v
                       结构 / 加粗 / 换行审计
                                  |
                                  v
                             通过后启用
```

旧模板版本继续保留：

```text
CN Guanzhi v1
CN Guanzhi v2
EN Guanzhi v1
EN Guanzhi v2
```

新模板不会破坏旧任务，历史文件可以继续按原 Profile 复现。

## 十二、推荐的程序模块边界

后续可以增加或拆分以下模块：

```text
template-registry.js
template-profile-cn-guanzhi-v1.js
template-profile-cn-guanzhi-v2.js
template-profile-en-guanzhi-v1.js
template-profile-en-guanzhi-v2.js
template-structure-validator.js
template-migration-report.js
```

其中：

- `template-registry` 管理模板版本、语言、公司和哈希；
- `template-profile-*` 管理特定版本的槽位、合并格、值格和结构策略；
- `template-structure-validator` 检查模板是否仍符合 Profile；
- `template-migration-report` 输出新旧模板的结构差异和需要确认的项目。

智能匹配引擎只输出：

```json
{
  "slotId": "s8:hand_protection",
  "value": "源文件值",
  "sourceLocator": "Section 8 row 3 cell 1",
  "status": "MATCHED"
}
```

模板适配器再决定实际目标值格：

```text
s8:hand_protection
    -> CN Guanzhi v1: row 3, right merged cell
    -> CN Guanzhi v2: row 4, right merged cell
```

## 十三、最终建议

要保证新模板结构变更后能够快速使用并且不和现有匹配规则冲突，必须遵守以下原则：

1. 新模板不覆盖旧模板，必须版本化并保存哈希。
2. 新模板先生成结构指纹和模板 Profile，再进入匹配。
3. 匹配规则只输出语义槽位，不直接使用模板行号和列号。
4. 标签格、值格、加粗区、非加粗区和合并关系必须由 Profile 明确声明。
5. 未知模板或结构漂移模板必须阻断正式匹配。
6. 新 Profile 必须使用真实 PU-2341E、PU-1107 等样例做回归。
7. 匹配完成后必须做模板前后结构、加粗、换行和空行审计。
8. 只有结构审计通过后，才允许导入编辑器和导出 DOCX。

最重要的一点是：程序不应该“猜测”新模板的值格。对于已登记模板版本，程序可以自动、快速、稳定地使用；对于未知结构，程序必须先完成 Profile 接入和验证。只有这样，模板变化才不会反过来污染当前的识别规则、语义映射规则和写入保护规则。

## 十四、标签和值识别的详细实施方案

模板结构能够被读取，并不等于程序已经知道哪个文本是标签、哪个文本是值。标签和值识别必须先建立证据模型，再计算关系。

### 1. 运行区证据模型

每一个 `w:r`、`w:t`、`w:br`、`w:tab` 都要保留原始定位和格式证据：

```json
{
  "runId": "document.xml:table[7]:row[3]:cell[0]:p[0]:run[2]",
  "text": "手部防护：",
  "bold": true,
  "italic": false,
  "font": "宋体",
  "sizeHalfPoints": "24",
  "paragraphId": "p-8-3-0",
  "cellId": "tc-8-3-0",
  "startOffset": 0,
  "endOffset": 5
}
```

必须保留：

- 原始文本；
- 是否加粗；
- 字体和字号；
- 段落编号；
- 所属段落和单元格；
- 在段落中的字符范围；
- 原始 XML 节点；
- 换行和制表节点；
- 图片和绘图关系。

这样后续即使同一段文字被拆成标签和值，也可以回到原始运行区核对，而不是只依赖拼接后的 `cell.text`。

### 2. 单元格证据模型

每个单元格至少保存：

```json
{
  "cellId": "tc-8-3-0",
  "xmlCellId": "tc-1234",
  "rowIndex": 3,
  "gridStart": 0,
  "colspan": 2,
  "rowspan": 1,
  "vMerge": null,
  "mergeGroupId": "merge-8-3-left",
  "paragraphCount": 1,
  "text": "手部防护：喷涂过程中要求有呼吸防护设备。"
}
```

`rowIndex`、`cell.col` 和底层 XML `tc` 不是同一个概念。尤其在 Word 合并单元格中，多个逻辑 cell 可能指向同一个 XML 单元格。后续定位值格时必须使用 `xmlCellId + gridStart + colspan`，不能只使用数组下标。

### 3. 标签候选与值候选分离

识别阶段不要直接生成最终的 `labelText` 和 `valueText`，而要先生成候选：

```json
{
  "candidateId": "label-0001",
  "kind": "label-candidate",
  "text": "手部防护：",
  "sourceCellId": "tc-8-3-0",
  "paragraphIndex": 0,
  "runIds": ["run-001"],
  "hasColon": true,
  "boldEvidence": true,
  "firstColumnEvidence": true,
  "confidence": 0.96
}
```

```json
{
  "candidateId": "value-0001",
  "kind": "value-candidate",
  "text": "建议戴上防护手套。",
  "sourceCellId": "tc-8-3-1",
  "paragraphIndex": 0,
  "runIds": ["run-002"],
  "boldEvidence": false,
  "rightOfLabelEvidence": true,
  "mergeGroupId": "merge-8-3-right",
  "confidence": 0.97
}
```

只有标签候选和值候选关系解析完成后，才能生成可供智能匹配使用的源事实。

## 十五、加粗与非加粗的判定规则

### 1. 加粗只是标签证据，不是标签结论

以下情况不能简单按“加粗就是标签”处理：

```text
燃烧时释放一氧化碳、二氧化碳和氮氧化物。
```

这可能是整段加粗的值或说明，而不是标签。

```text
pH值（1%水溶液）：7-9
```

整段可能被 Word 保存成同一套加粗运行区，程序仍需按冒号和语义范围切分标签和值。

```text
加粗值列内容
```

值单元格中的加粗文字也不能自动变成标签，必须结合列位置和模板 Profile。

### 2. 非加粗也不一定是值

非加粗文字可能是：

- 表格列标题；
- 单列说明行；
- 页眉页脚；
- 续行；
- 结构说明；
- 表头；
- 图片旁的说明文字；
- 模板示例值。

因此角色判定必须综合：

```text
加粗状态
是否以冒号结束
文本长度
是否有数字前缀
所在列
是否位于表头
是否位于第一网格列
是否与其他候选位于同一行
是否存在相邻值格
Section 语义
模板 Profile
```

### 3. 标签候选的正向证据

- 短文本且以冒号结束；
- 处于第一网格列；
- 具有 Word 自动编号；
- 加粗且后面存在非加粗文本；
- 匹配当前 Section 的已登记别名；
- 与右侧或下方值候选形成稳定关系；
- 模板 Profile 标记为标签格。

### 4. 标签候选的负向证据

- 长句且没有冒号；
- 含有多个数值和单位；
- 含有句号、分号等完整句式；
- 位于值列或合并值格；
- 同一行已有明确标签，而该文本出现在标签之后；
- 是一整段毒理、消防或废弃说明；
- 是表头或 Section 标题。

### 5. 值候选的正向证据

- 处于标签右侧；
- 处于同一段落的标签冒号之后；
- 处于同一物理行的后续合并单元格；
- 是一个完整技术句子；
- 包含数值、单位、代码或测试结果；
- 位于模板 Profile 标定的非加粗值格；
- 与标签候选的段落序号能够配对。

加粗和非加粗都只能增加或降低置信度，不能单独决定角色。

## 十六、标签和值关系解析器

标签和值关系不能只按行号匹配，应该建立关系图。

### 1. 支持的关系类型

```text
same-paragraph-inline
same-cell-label-then-value
same-row-adjacent-cells
same-row-merged-label-value
continuation-row
multi-column-record
child-label-value
section-note
source-only
```

### 2. 同一段落

```text
pH值：7-9
```

处理方式：

1. 冒号前生成标签候选；
2. 冒号后生成值候选；
3. 保存原始字符范围；
4. 防止把 `12:00`、`1:1`、URL 和标准号中的冒号误判为分隔符。

### 3. 同一单元格多个段落

```text
标签
值
```

只有在段落顺序明确、标签和值角色明确时才能配对。如果同一单元格出现多组标签和值：

```text
标签 A
值 A
标签 B
值 B
```

必须按段落顺序配对，不能把整个单元格拼成一个值。

### 4. 同一行相邻单元格

```text
标签 | 值
```

必须同时满足：

- 两个单元格属于同一个物理 XML 行；
- 标签格处于较小的网格起始列；
- 值格位于标签格右侧；
- 两者不是同一个合并 XML 单元格；
- 值格不是表头或固定结构格；
- 值格存在可写的值运行区。

### 5. 合并单元格

Section 8 这类结构不能这样写：

```javascript
const valueCell = row.cells[1];
```

必须使用：

```text
xmlCellId
gridStart
colspan
rowspan
mergeGroupId
labelRole / valueRole
```

写入前强制检查：

```text
targetCell.xmlCellId !== labelCell.xmlCellId
targetCell.gridStart > labelCell.gridStart
targetCell.role === value
targetCell.colspan > 0
```

任何一项不满足，写入计划进入 `UNSAFE_STRUCTURE`，不得继续写入。

### 6. 续行

只有下面条件全部满足，才允许把下一行追加到上一行值：

```text
当前行第一网格列为空；
当前行后续网格列有值；
上一行已经形成明确的标签和值关系；
当前行不是表头；
当前行没有自己的标签；
当前行合并结构与上一行兼容。
```

以下内容必须保持独立：

```text
氟化橡胶-FKM | 厚度……
丁基橡胶-IIR | 厚度……
```

因为它们都有自己的标签。

### 7. 同行多个标签和值

如果标签数量和值数量相等，应按段落序号、网格列和合并范围配对。如果数量不相等：

```text
标签数量 = 3
值数量 = 2
```

不能使用最近邻强行补配，应进入 `AMBIGUOUS` 或 `UNSAFE_STRUCTURE`。

## 十七、关系评分和冲突处理

关系评分可以帮助排序，但不能绕过硬约束。示例评分因素：

```text
+40 同一段落存在明确冒号
+35 加粗标签后紧跟非加粗值
+30 同一物理行的右侧值格
+25 同一合并记录中的标签格和值格
+20 模板 Profile 明确指定关系
+15 Section 语义别名精确命中
+10 值含数值、单位或专业代码
-40 Row 0 或表头
-40 标签和值共享同一标签保护 XML 节点
-35 值位于第一网格列标签区域
-30 候选目标已被其他事实占用
-25 标签候选是长句
```

最终状态建议统一为：

```text
MATCHED
MATCHED_TRANSFORMED
SOURCE_ONLY
EMPTY
AMBIGUOUS
CONFLICT
UNSAFE_STRUCTURE
```

如果两个源事实竞争同一个目标槽位，或者同一行存在多个等分关系，不能静默覆盖，必须保留冲突和来源位置。

## 十八、写入计划和安全写入

匹配完成后不能直接调用 `writeCellValue()`，必须先生成写入计划：

```json
{
  "sourceFactId": "FACT-0032",
  "section": 8,
  "slotId": "s8:hand_protection",
  "sourceText": "建议戴上防护手套。",
  "targetCellXmlId": "tc-8-3-right",
  "targetRole": "value",
  "targetIsBold": false,
  "transform": "none",
  "preserveLineBreaks": true,
  "status": "READY"
}
```

写入前检查：

- 目标 XML 单元格是否存在；
- 目标是否真的是值格；
- 目标是否不是标签格；
- 目标是否允许写入；
- 是否有其他源事实占用目标；
- 是否需要保留换行；
- 是否需要 Section 特殊规则；
- 是否需要人工批准。

### 值写入

普通值只能写入值格的非加粗运行区：

- 只清空值运行区；
- 不清空标签运行区；
- 不重建表格；
- 不调用 `cell.text = ...`；
- 不调用 `paragraph.text = ...`；
- 不用空格或制表符假对齐；
- 保留合并关系、列宽、行高和段落属性。

### 标签写入

标签和序号默认只读。只有模板 Profile 明确允许的 Section 9 测试条件，且源文件明确提供限定词时，才允许受控修改标签。其他 Section 即使源标签名称不同，也不能直接改写模板标签来适应源文件。

### 换行写入

有意义的源换行应写入同一 Word 段落中的 `w:br`：

```text
值段落
  文本 A
  w:br
  文本 B
  w:br
  文本 C
```

不能把一个逻辑值拆成多个段落，否则容易产生额外段距、分页和行高异常。

## 十九、空值、剪枝和结构行处理

空值必须区分：

### 1. 源文件没有字段

例如 Section 10.4 完全不存在。按 Section 规则删除完整项或隐藏整行。

### 2. 源文件明确写“无数据”

例如 Section 9 的 `无数据`。Section 9 可以按专门规则剪枝；其他 Section 必须按 Profile 决定显示标准缺失话术还是隐藏。

### 3. 源文件有实质否定结论

例如：

```text
无危险反应
非危险品
初沸点以下无闪点
```

这些不是缺失，不能被剪枝或改成“无数据”。

每个剪枝动作必须记录：

```json
{
  "slotId": "s9:evaporation_rate",
  "sourceStatus": "MISSING",
  "action": "PRUNED",
  "deletedTargetRow": true,
  "targetRowAfterRenumber": null
}
```

最终必须满足：

```text
prunedFields = 实际隐藏或删除的目标项数量
```

如果统计为 15 个剪枝、实际只删除 10 行，必须阻断导出并报告差异。

## 二十、六类问题的自动审计器

新流程应直接把用户关注的六类问题变成自动审计规则。

### 类别 1：标签和值错位

检查：

- 值文本是否出现在标签格；
- 标签文本是否出现在值格；
- 值格是否与标签格使用同一个 XML 单元格；
- 同行值是否落在标签左侧；
- 同级子标签是否被合并到另一个子项；
- 表头是否被值内容替换。

### 类别 2：源有值但目标缺失

检查：

- 每个 substantive source fact 是否有目标槽位；
- 目标槽位是否有写入值；
- 源值是否只出现在隐藏模型而没有出现在结果页面；
- 源值是否被另一个槽位占用；
- 源值是否被剪枝但没有合法剪枝理由。

### 类别 3：换行错误

检查：

- 源有逻辑换行而目标没有；
- 源只有一个换行而目标产生双换行；
- 值被拆成多个 Word 段落；
- 值被拼成长句；
- 合并单元格窄列导致异常逐字换行；
- 视觉换行和语义换行是否被混淆。

### 类别 4：未经授权的原文改写

检查：

- 源标签是否被改写；
- 源值是否被替换成模板值；
- `无数据` 是否变成 `不适用`；
- 测试条件是否来自源文件；
- 标准化改变是否存在批准的 transformation policy；
- 非允许 Section 是否发生拼接、拆分或语义改写。

### 类别 5：无值标签未隐藏

检查：

- 源没有字段但目标标签仍可见；
- 目标值格为空但标签行没有删除；
- 剪枝统计和实际删除行数不一致；
- 空标签是否属于允许保留的结构标题；
- 删除后合并结构和序号是否仍然有效。

### 类别 6：加粗结构被篡改

检查：

- 原模板加粗标签是否消失；
- 原模板非加粗值是否被改成加粗；
- 值是否进入原加粗标签运行区；
- 同级加粗子标签是否被清空；
- 表头加粗角色是否被普通值覆盖；
- 加粗运行区的文本和顺序是否发生变化。

## 二十一、推荐实施阶段

### 阶段 1：证据模型

目标：不改变现有界面，先让解析结果保留完整 XML 和角色证据。

交付：

- `RunEvidence`；
- `ParagraphEvidence`；
- `CellEvidence`；
- `MergeGroup`；
- `SourceFact`；
- 原始来源定位。

### 阶段 2：候选角色识别

目标：把当前直接返回的 `labelText/valueText` 改成候选集合和置信度。

交付：

- 标签候选生成器；
- 值候选生成器；
- 冒号保护；
- 自动编号解析；
- 长句和说明行识别；
- 表头、标题和页眉页脚过滤。

### 阶段 3：关系解析

目标：确认一个值属于哪个标签。

交付：

- 同段关系；
- 同格多段落关系；
- 同行相邻格关系；
- 合并格关系；
- 续行关系；
- 多标签多值关系；
- 冲突和歧义状态。

### 阶段 4：模板 Profile

目标：让模板结构独立于语义匹配。

- Section 槽位 Profile；

- 合并关系；
- 加粗和非加粗写入策略；

- 行删除计划；

### 阶段 6：六类自动审计

目标：把本报告中的问题变成导出前自动门禁。

## 二十二、验收标准

新机制至少要通过以下验收：

1. PU-2341E 的 Section 3 表头 `CAS编号` 不被组分汇总覆盖；
2. Section 8 的手部防护值不进入标签列；
3. Section 11 的生育力、致畸形和体外遗传毒性加粗子标签保留；
4. 源文件有值的 Section 5.1、8 建议、9 相对密度能够追踪到目标值格；
5. Section 5.4、6.1、7.1、13 的源换行经过明确策略处理；
6. Section 9 的测试限定词只有源文件明确提供时才会写入标签；
7. Section 10 无值项按规则删除或隐藏；
8. 无值剪枝数量和实际隐藏/删除数量一致；
9. 模板加粗运行区前后差异为零，除明确授权的 Section 9 标签限定词；
10. 任何 `UNSAFE_STRUCTURE`、`AMBIGUOUS`、`CONFLICT` 都会阻止导入或导出；
11. 新模板结构变更后可以通过新 Profile 接入，不需要修改已有语义槽位定义；
12. 旧模板版本仍可以重新打开历史任务并获得一致结果。

## 二十三、最终原则

程序不应该猜测新模板的值格，也不应该把加粗、行号或数组位置当成唯一依据。

可靠的确认顺序必须是：

```text
先确认文本证据
    |
    v
再确认标签候选和值候选
    |
    v
再确认同段、同格、同行、合并格和续行关系
    |
    v
再确认语义槽位
    |
    v
再根据模板 Profile 找真实值格
    |
    v
生成写入计划
    |
    v
通过六类审计后写入和导出
```

对于已登记模板版本，程序可以快速、稳定地使用；对于未知或结构漂移模板，程序必须先完成 Profile 接入和验证。只有这样，模板结构变化才不会污染现有识别规则、语义映射规则、加粗保护规则和写入逻辑。
