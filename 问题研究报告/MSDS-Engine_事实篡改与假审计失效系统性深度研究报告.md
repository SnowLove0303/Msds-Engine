## 一、 执行摘要与事件回溯

在执行源文件 `"PU-608 msds_CN 冠志.docx"` 向标准 8 格式（4 DOCX + 4 PDF）交付物受控生产的任务中，系统初次执行后出具了全绿通过的终审报告。然而，在用户进行人工质检时，**当场捕获到致命内容违章**：

> 用户反馈：*“你做审计没有，怎么内容又对不上，你真识别了吗，你真调用MSDS-Engine 了吗”*

经过对产出文档与源文件的逐字物理比对，确认：
1. **源文件事实**：PU-608 为生殖毒性危品，含有 N-甲基吡咯烷酮（NMP），其毒理学实测数据为**经口 LD50 4,150mg/kg、吸入 LC50 >5.1mg/l、经皮 LD50 >5,000mg/kg、造成皮肤刺激、严重的眼睛刺激、小鼠致敏阴性、NMP 有经皮吸收危险**；

3. **质检工具表现**：双极双层全景机械审计脚本 (`audit_bipolar_bilayer.mjs`) 与 MCP 对账工具 (`msds_compare_source_with_output`) **双双给出了 100% 满分通过，未报告任何 Gap**。

这是一起典型的**“业务层硬编码伪造数据 + 审计层弱断言同谋假放行”**的严重工程事故。

## 三、 深度 5-Whys 根因穿透分析

为彻底根治此问题，必须顺着因果链深入穿透到制度与认知层面：

### 3.1 第一问：为什么 PU-608 的毒理数据被篡改成了 PU-202A 的数据？
- **直接原因**：在 `web/src/pipeline-engine.js` 的第 1327~1426 行中，执行 Section 11 排版时，代码使用了字面值常量直接调用 `writeStructuredToxicologyCellValue(vCell, '半数致死剂量（LD50）/大鼠：3,000－6,000mg/kg', ...)`，把单元格原有的真实内容完全清空并覆盖。

### 3.2 第二问：为什么核心业务引擎中会出现硬编码常量？
- **工程债动因**：在开发初期针对 `PU-202A` 进行单样本攻坚时，为了在最短时间内使 PU-202A 达到“15行严格同构（L-S11）”的视觉完美排版，开发者为了图快，没有走“从源文件解析值 $\to$ 数据结构清洗 $\to$ 注入模板”的正规通用管线，而是**直接把 PU-202A 源文件里的文字原样复制粘贴成了代码里的字符串字面量**。
- **侥幸心理**：开发者当时认为“先跑通这个产品再说”，留下了技术债务。

### 3.3 第三问：为什么原有的通用动态逻辑完全不生效？
- **代码结构遮蔽**：在 `pipeline-engine.js` 中，存在严重的死代码（Dead Code）：
  ```javascript
  // 第 1307 行的分支：
  if (s11 && s11Paradigm !== 'PARADIGM_1_FULL_WIDTH_MERGED' && !isNonHazComposite) {
    // 这里塞满了 PU-202A 的硬编码！
  }
  // ...
  // 第 1460 行的分支：
  else if (s11 && !isNonHazComposite && s11Paradigm !== 'PARADIGM_1_FULL_WIDTH_MERGED') {
    // 这里才是原本应该运行的通用动态逻辑！
  }
  ```
  由于第 1307 行和第 1460 行的判断条件完全一模一样，第 1460 行的分支**在控制流上被 100% 遮蔽，根本永远不可能被执行到**！

### 3.4 第四问：为什么双极双层审计脚本会报满分通过？
- **断言设计缺陷（弱断言欺诈）**：在 `web/scripts/audit_bipolar_bilayer.mjs` 第 792 行：
  ```javascript
  assert(/急性毒性|刺激性|毒性/i.test(s11Cn.textContent), 'Section 11 (L-S11): 毒理学测试数据保全');
  ```
  审计脚本只检验了文本中是否出现“急性毒性”或“刺激性”这几个字。因为篡改后的 PU-202A 假数据里同样包含“急性毒性”和“刺激性”，所以断言直接绿灯通过。**审计验证的是“词汇存在性”，而非“事实正确性”**。

### 3.5 第五问：为什么 MCP 事实物理对账工具会报告 0 Gap？
- **对账粒度宏观化（字数假象）**：在 `web/src/mcp-server.js` 的 `msds_compare_source_with_output` 中：
  ```javascript
  if (sText.length > 50 && oText.length < 20) {
    actionableGaps.push({ ... });
  }
  ```
  工具仅在“源文本大于 50 字且输出文本小于 20 字”时才报警。源文件 Section 11 是 497 字，产出物被塞入假数据后是 513 字，工具对比结果为 `497 vs 513`，字符保全比 103.2%，直接判定无 Gap。**宏观统计学对账在结构性内容替换面前彻底失效**。

## 四、 假审计的两大病理剖析（弱断言欺诈与字数假象）

### 1. 弱断言欺诈（Trivial Assertion Fraud）
弱断言是指：**即便业务逻辑发生 100% 的颠覆性错误，断言依然能够给出通过结论的测试。**
- **典型表现**：
  - 断言 `/\d+/` 来证明包含了测试数值（无论数字是 1 还是 10000 都通）；
  - 断言 `/毒性/` 来证明毒理学数据完整（哪怕全篇内容是毒理数据被篡改的假文）；
  - 断言 `table.rows.length >= 12` 证明表格排版正确（即便里面的每一行都是错的）。
- **危害**：弱断言制造了虚假的安全感，不仅无法防范 Bug，反而成为了掩盖严重 Bug 的“合法防空洞”。

### 2. 宏观字数与字符保全比的幻觉
- 在许多自动化对账体系中，经常采用 `fidelityRatio = outputChars / sourceChars` 的计算方式；
- 这种计算方式的前提假设是“模型只会遗漏，不会胡编”。但在有模板套用或硬编码残留的场景下，**将正确内容替换为错误内容，字符数完全可以保持一致甚至增加**；
- 如果不对关键名词实体（CAS 号、化学品名、数值、受试动物、定性结论）建立微观物理核销，宏观字数对比就是毫无意义的数字游戏。

## 五、 架构重构与治本方案实施细节

针对上述五大根因，实施了全方位的架构立法与代码改造，所有改动均已通过 VS Code 原生 Diff Editor 检阅确认：

### 1. 核心业务引擎去特化 (`web/src/pipeline-engine.js`)
- **废除硬编码**：彻底剔除 lines 1327~1426 中的所有字符串常量；
- **合并遮蔽分支**：将第 1307 行与第 1460 行的双重分支合二为一，统一为唯一的单组分表格排版管线；
- **纯动态数据驱动**：单元格保持 `smart-matching.js` 匹配提取的原值：
  ```javascript
  let oralRow = s11.rows.find(r => /经口/i.test(r.cells.map(c => c.text).join(' ')));
  if (oralRow) {
    const vCell = oralRow.cells[oralRow.cells.length - 1];
    const val = vCell?.text?.trim() || '';
    if (val) writeStructuredToxicologyCellValue(vCell, val, { isEnglish: false });
  }
  ```
- **经皮英译感知**：升级 `translateToxicologyValueToEnglish(cnText, endpoint)`，在处理 Dermal 行时准确将大鼠 LD50 英译为 `LD50 / Dermal / Rat: > 5,000mg/kg`，彻底消除误译为 Oral 的缺陷。

### 2. 升级双极双层审计至实体基准事实级别 (`web/scripts/audit_bipolar_bilayer.mjs`)
- 废黜 `assert(/急性毒性|刺激性|毒性/)` 弱断言；
- 建立产品事实指纹（Fact Fingerprint）断言：
  ```javascript
  if (model === 'PU-608') {
    assert(/4,150|4150/.test(s11Cn.textContent), 'PU-608 经口急性毒性实测值 4,150mg/kg 保全');
    assert(/造成皮肤刺激/.test(s11Cn.textContent), 'PU-608 皮肤刺激实测事实“造成皮肤刺激”保全');
    assert(/严重的眼睛刺激/.test(s11Cn.textContent), 'PU-608 眼睛刺激实测事实“严重的眼睛刺激”保全');
    assert(/经皮吸收危险/.test(s11Cn.textContent), 'PU-608 附加信息“经皮吸收危险”保全');
  }
  ```

### 3. MCP 工具建立穿透式定量与定性对账 (`web/src/mcp-server.js`)
- 在 `msds_compare_source_with_output` 中增加第 11 节实体级自动对账机制：
  1. 正则自动提取源文件中所有测试数值（如 `\d+(?:[.,]\d+)?mg/kg`）；
  2. 提取源文件中关键定性危害结论（如“造成皮肤刺激”、“严重的眼睛刺激”、“经皮吸收危险”）；
  3. 核对这些实体在产出物中的物理存在性；若有缺失，立即阻断并上报 `FACTUAL_INCONSISTENCY` 行动差距。

## 七、 经验教训与防线下沉防线机制

为确保全系统永久具备针对同类隐蔽缺陷的免疫力，依据 **Lauren Tan (@poteto) 防线下沉自迭代准则**，固化以下规则：

1. **Layer 1（架构级：去特化与事实守恒定律）**：
   - 严禁在任何业务处理流程（`pipeline-engine.js`、`smart-matching.js`）中写入特定型号的测试数据常量；
   - 核心 Engine 仅作为“结构排版与几何装配器”，业务数据的唯一合法来源必须是 `recognition-engine` 从源文件中提取的事实。
2. **Layer 2（静态分析级：纠错两次即立项为门禁）**：
   - 在代码审查中，凡出现针对特定测试用例值的字面量赋值，视为严重代码坏味道；
   - 后续将开发专用 AST 检测探针，扫描全库严禁出现硬编码毒理数值常量。
3. **Layer 4（自验证级：变异元审计 Prove It Works）**：
   - 编写审计脚本时，必须实施变异测试（Mutation Test）：将输出文档中的关键数值临时置空或改错，验证审计脚本是否能立刻触发红灯拦截；凡是在变异状态下依然输出 PASS 的断言，一律判定为“弱断言欺诈”并重构。
4. **Layer 5（物理核销级：实体级 Fact Fingerprint RTM）**：
   - 所有化学品交付物验收，必须出具包含所有实测定量数值（LD50/LC50/EC50）和定性结论的 1:1 物理核销表格，杜绝以宏观字数相似替代微观事实对账。
