## 零、全局匹配规则的核心使命与“两遍架构” (The Two-Pass Architecture)

在 MSDS 处理链路中，源文档格式千差万别（非标表格、OCR 多栏扫描、键值挤压、序号乱跳），而目标输出是具有严格几何锁定的 16 节标准模板（CN/EN 冠志/国彩）。
**智能匹配（Smart Matching）是连接“源抽取”与“模板覆写”的唯一中间层枢纽。**

为杜绝直接操作 DOCX 造成的样式污染与逻辑错位，全局匹配必须严格执行**两遍架构（Two-Pass Architecture）**：

```
┌───────────────────────────────────────────────────────────────────────────────────┐
│                      【第一遍：不动 DOCX，纯语义抽取与对齐】                        │
│                                                                                   │
│  非标源提取 ──► [事实解构与清洗] ──► [语义槽位对齐] ──► [状态判定/剪枝标记] ──► 标准匹配载荷  │
│                   (Run/Colon/换行)     (别名库/去噪)      (MATCHED/PRUNED)       (MODEL.json)   │
└─────────────────────────────────────────┬─────────────────────────────────────────┘
                                          │ 审阅确认 / 自动化门禁通过 (Fail-Closed)
┌─────────────────────────────────────────▼─────────────────────────────────────────┐
│                      【第二遍：受控原位注入，几何与重排】                           │
│                                                                                   │
│  标准匹配载荷 ──► [克隆基准模板] ──► [写入12pt非加粗值] ──► [安全删行剪枝] ──► [连贯重排与审计] │
│                   (SHA-256保护)       (标签绝对硬锁)         (倒序删行)           (N.1/N.2递增)   │
└───────────────────────────────────────────────────────────────────────────────────┘
```

## 一、源事实解构与多模态切分全局规则 (Fact Decomposition Rules)

无论面对表格单元格、散文段落还是混杂文本，全局匹配引擎必须依据以下原子规则将源文本解构为标准键值对：

### 1.1 样式角色分离解构 (Run-level Role Separation)
- **同段内粗细分离**：若段落首部包含加粗运行区（`run.bold = true`），而尾部包含常规体运行区（`run.bold = false`），引擎强制切分为两部分：
  - 加粗部分识别为 **候选标签 (Candidate Label)**；
  - 常规体部分识别为 **实证数值 (Candidate Value)**。
- **跨段粘连识别 (Adjacent Paragraph Bonding)**：若段落 $i$ 仅有加粗文本且以冒号结尾或无后续值，而紧邻段落 $i+1$ 为常规体文本，引擎自动将其关联为单个键值对，杜绝孤儿标签。

### 1.2 行内冒号语法解耦 (Inline Colon Splitting)
- **切分通用正则**：`^\s*([^：:\n\t]{1,100}?)[：:]\s*([\s\S]+?)\s*$`；
- **业务符号保护**：
  - 严禁将化学物质配比（如 `1:1`、`25:75`）、时间戳（`12:00`）、化合物名称中的冒号误断为分隔符；
  - 冒号左侧为标签，冒号右侧为数值；若右侧为空，则转入跨段关联或空值处理。

### 1.3 前缀噪声剥离与主序脱敏 (Prefix Sanitization)
- **前缀清洗正则**：`^\s*(?:v\s*)?\d+(?:[.．、]\d+)*(?:[.．、])?\s*` 以及 `^[（(]?[0-9一二三四五六七八九十]+[）)]?[.、\s]?`；
- **脱敏比对**：在与标准槽位别名字典进行比对时，必须彻底剥离源文件自带的各种非标序号（如将 `9.3 pH值：` 或 `3、pH值` 统一剥离为纯净语义词 `ph值`）；
- **溯源保留**：剥离仅用于比对，原始抽取上下文必须完整保留在 `sourceText` 中，以供全量追溯。

### 1.4 多标签与多值合并行扁平化 (Multi-Entity Flattening)
- 当源文档将多个属性挤压在一个单元格中（常见于小作坊 MSDS 将 5 项理化指标写在一个单元格内）：
  - 引擎必须依据换行符与冒号语法进行次级循环解构，拆解为 $N$ 个独立的平铺事实，严禁整坨作为单个大字段塞入模板。

## 二、语义槽位注册与别名智能对齐全局规则 (Slot Binding & Alias Matching)

### 2.1 槽位权威注册表 (Canonical Slot Registry)
- Section 1 ~ 16 严格预设标准唯一的 `Slot ID`（如 `s1:product_name`, `s2:signal_word`, `s8:respiratory_protection`, `s9:flash_point` 等）；
- 每个标准槽位绑定跨语言、跨行业的权威别名字典库（Alias Group），包含全称、简称、缩写与中英文常见变体。

### 2.2 标签语义归一化 (Label Normalization Algorithm)
在查询别名字典前，源标签必须通过统一归一化函数进行无损降噪：
1. 剥离数字序号前缀（见 1.3）；
2. 彻底剔除全半角标点符号：`[：:、，,。；;（）()\[\]【】—–\-_/\\ \s\t\r\n]`；
3. 全部转为纯小写字符串；
4. 例如：`9.17 动力粘度（25℃）：` 归一化为 `动力粘度`（测试条件 `25℃` 被提取至限定词属性）。

### 2.3 语义优先，严禁位置推断 (Semantic Over Position)
- **OW-029 铁律**：**严禁仅按表格物理行号进行位置匹配！**
- 绝对禁止写出 `target_row = source_row[3]` 这类位置型 Payload；
- 每一个映射动作必须明确指明目标章节（Target Section）与目标插槽（Target Slot ID）；未命中注册表的字段直接进入未决评审队列，严禁随机顺序顺延。

### 2.4 独占性与多义冲突裁决 (Exclusivity & Conflict Resolution)
- **单一独占原则**：一个源事实原则上只能绑定一个模板插槽；
- **重复定义冲突**：若源文档出现两处相同标签（例如有两个不同的“密度”测定值），必须检查测试条件（限定词）；若条件不同则尝试分行映射，若条件相同且数值冲突，标记为 `REVIEW_AMBIGUOUS` 并阻断发布，严禁静默覆盖。

## 三、数值清洗、格式规整与业务真值保护全局规则 (Value Normalization)

### 3.1 字符净化与空白标准化
- 自动剔除两端无效空白、制表符、零宽空格（`\u200b`）、BOM 标记（`\ufeff`）；
- 统一将段落内的 `\r\n` 与 `\r` 归一化为标准的单换行符 `\n`；
- 严禁出现连续重复空格与行末悬挂空格。

### 3.2 业务换行保真
- 源文档中具备业务含义的换行（如危害说明逐条列出、急救措施分步描述），在值单元格内必须作为**软换行符**保留，严禁直接粗暴拼接成无标点的单行长文；
- 严禁为了凑版式而人为添加多余的空段落（Empty Paragraph）。

### 3.3 合成斜杠转换与固有词组保护
- **列表型斜杠转换**：源文档中作为多项并列的斜杠分隔（如 `A / B / C` 或 `通风 / 排气`），在映射时需识别为多行独立条目；
- **固有词组保护**：对于行业固有名词（如 `公路/铁路运输`、`有/无`、`固态/气态`、`水/辛醇`），严禁拆开，原样保留；
- **孤儿占位阻断**：若值单元格清洗后仅剩下单个 `/`、`／`、`-` 或 `—`，判定为非法占位符，强制清空并转入缺失处理。

### 3.4 度量衡与化学语法高保真
- 绝对保真数值范围符号（`7.0 - 9.0`、`100 ~ 120 ℃`）、不等号（`> 100`、`< 0.1%`、`≤ 50 mg/kg`）；
- 保持国际单位制格式规范（`mPa·s` 或 `mPa.s`、`g/cm³`、`mg/m³`），严禁在匹配过程中发生度量单位丢失。

## 四、缺失识别、未测判定与实质否定结论全局区分规则 (Missing vs. Negative)

全局匹配引擎必须具备辨别“真正的数据缺失”与“合规的实质性否定结论”的能力，这是保障合规质量的关键：

### 4.1 纯缺失占位符识别准则
- **核心判定正则**：
  `^(?:无数据(?:资料)?|暂无数据|无可用数据|无适用资料|未测定?|未做测定|未提供|尚无资料|/|—|-|no data available|not available|none)$`
- 命中上述判据的值，代表源文档在该字段上**无实际测定或事实支撑**。

### 4.2 缺失 vs 实质否定结论的黄金分水岭

| 类型 | 典型源文档表述 | 判定动作 | 业务合规意义 | 处理规则 |
| :--- | :--- | :--- | :--- | :--- |
| **纯缺失<br>(Missing)** | `无数据`、`暂无数据`、`未测`、`—`、`No data` | 标记 `PRUNED` 或 `EMPTY` | 未做实验或缺乏数据 | Section 9 等章节安全整行剔除；其他章节不显示或保留标准客户面话术。 |
| **实质否定结论<br>(Negative)** | `不适用 (Not applicable)`<br>`非危险品`<br>`无危险反应`<br>`初沸点以下无闪点`<br>`未满足分类标准`<br>`无刺激 / 无致敏性` | 必须标记 **`MATCHED`**<br>(绝不得剪枝！) | **具备权威实证的合规结论**（证明经测试安全或依法无需分类） | **100% 完整保留在标准模板对应值格中**，严禁误判为缺失而剔除！ |

## 五、状态机流转与六大处置动作全局规则 (Action Code Engine)

每一个源事实经过匹配计算后，必须被赋予唯一的处置动作代码（Action Code），驱动后续的审查与注入：

```
       ┌──────────────────────── 源事实输入 ────────────────────────┐
       │                                                           │
       ▼                                                           ▼
[命中标准插槽?]                                             [未命中标准插槽]
  ├── 是 ──► [是否包含有效数值?]                                   │
  │            ├── 是 ──► [是实质否定结论?]                        ▼
  │            │            ├── 是 ──► 【MATCHED】(保留结论)   【UNMATCHED / EXTRA】
  │            │            └── 否 ──► 【MATCHED】(常规写入)   (记录为额外数据，备查)
  │            └── 否 ──► [属于需要剪枝的章节(如S9)?]
  │                         ├── 是 ──► 【PRUNED】(安全删行)
  │                         └── 否 ──► 【EMPTY】(标准无数据)
  │
  └── 歧义/冲突/无法判定 ─────────────────────────────────────► 【REVIEW_AMBIGUOUS】
                                                               (人工拦截审校)
```

1. **`MATCHED` (精准匹配)**：
   - 精确命中标准插槽且包含有效测定数据或实质否定结论；
   - 动作：将规整后的值原位写入模板对应的可编辑值格。
2. **`PRUNED` (安全剪枝)**：
   - 命中插槽但值为纯缺失占位符，且所在章节规则明确要求剪枝（如 Section 9 理化特性）；
   - 动作：在第二遍覆写中整行安全删除，后续触发连贯重排。
3. **`EMPTY` (缺席留空)**：
   - 源文档未提供该字段，但该字段属于模板固定骨架；
   - 动作：值单元格保持清空或写入客户面标准 `无数据` / `No data available`。
4. **`NOT_APPLICABLE` (明确不适用)**：
   - 源文档明确标注为“不适用”；
   - 动作：完整保留写入值格，作为合规凭证。
5. **`UNMATCHED / EXTRA` (非标多余项)**：
   - 源文档提供了额外条目，未在 16 节标准模板几何中找到对应插槽；
   - 动作：不随意破坏模板插入新行，暂存至 `extra_facts` 队列或归集到各节的“其他信息/附加信息”注槽中。
6. **`REVIEW_AMBIGUOUS` (歧义阻断)**：
   - 出现一词多义、多源冲突或无法明确归类的条目；
   - 动作：强制拦截，生成审查警报，等待人工干预确认。

## 六、非结构化长文本与说明性段落分类归集全局规则 (Note Routing)

源文档中经常存在大量跨越表格之外的免责声明、法规列表或说明段落。匹配引擎建立**全局注槽分类器 (Narrative Note Dispatcher)**，按语义将非标签段落智能路由至模板中的单格注槽：

- **毒理可用性说明 (`s11_availability`)**：
  - 匹配模式：`无可用的毒理学研究|未进行毒理学试验|该产品无毒理数据`；
  - 路由目标：Section 11 导引说明注槽。
- **生态可用性说明 (`s12_availability`)**：
  - 匹配模式：`无可用的生态毒理学研究|未进行生态测试`；
  - 路由目标：Section 12 导引说明注槽。
- **类似产品参考依据 (`s11/s12_reference`)**：
  - 匹配模式：`类似产品.{0,20}(?:毒理|风险评估|参考数据)|结构类似物`；
  - 路由目标：Section 11 / Section 12 的参考数据受控注槽。
- **法规符合性清单 (`s15_regulation`)**：
  - 匹配模式：`GB/T|国务院令|危险化学品安全管理条例|新化学物质环境管理登记办法`；
  - 路由目标：Section 15 `符合下列法规要求：` 注槽。
- **通用免责声明 (`s16_disclaimer`)**：
  - 匹配模式：`上述信息依据我们目前所知|使用者应自行负责|仅供参考`；
  - 路由目标：Section 16 `其他信息` 注槽。

## 七、跨语言双向对齐与术语一致性全局规则 (Bilingual Semantic Alignment)

为了支撑八格式矩阵（4 DOCX + 4 PDF）的同源一致性，匹配引擎必须在第一遍就完成双语语义模型的对齐：

1. **Slot ID 绝对同构**：中文模板与英文模板采用完全一致的槽位编号系统（如 `s9:flash_point` 在 CN/EN 下完全等价）；
2. **技术事实 100% 对齐**：数值、温度、浓度比、CAS 号在双语模型中共享同一数据节点，杜绝中英文出现两套技术指标；
3. **专业 SDS 术语层标准化**：
   - 英文映射强制经过专业翻译字典库（`professional_translation_glossary`）；
   - 常见状态统一对齐：`无数据` ➔ `No data available`；`不适用` ➔ `Not applicable`；`无` ➔ `None`；`未分类` ➔ `Not classified`；
4. **严禁中文派生**：绝不通过中文 DOCX 渲染物翻译生成英文，必须由本语义匹配模型同时向 CN 模板和 EN 模板独立灌入！

## 八、匹配结果向覆写引擎交接的注入契约 (Engine Handoff Contract)

当第一遍匹配完成且人工在三模块同屏对照工作台审阅确认后，匹配引擎输出标准化的 `MatchResult` 载荷，通过注入适配器与模板引擎对接：

1. **模板实例无损挂载**：适配器接收克隆好的干净模板引擎（`DocxEngine`），此时模板具有完整原始 XML 结构、样式与 325 处加粗标签锁；
2. **常规值原子写入**：遍历所有 `MATCHED` 状态的项，通过 `writeCellValue(cell, value, roleStyles.value)` 注入值，强制应用 **12pt 非加粗** 样式；
3. **剪枝项自底向上安全删除**：针对所有标记为 `PRUNED` 的项，收集行索引并**倒序（从大到小）**调用 `deleteRow(engine, record, rowIndex)`，防止因删行导致后续行号漂移；
4. **连贯重新编号触发**：删行完成后，立即触发 `renumberRecord(record)`，将存活行自动重排为连贯的 `N.1, N.2, N.3...` 序号；
5. **合规审计校验与归档**：调用 `auditEngine(engine)` 确认 16 章节几何完整性、无断号、无加粗污染，最终无缝进入模板编辑器或直接导出 DOCX。
